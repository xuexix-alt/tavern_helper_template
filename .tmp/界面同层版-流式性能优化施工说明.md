# 寒冬末日｜界面同层版 · 流式传输性能优化施工说明

> 文档目的：把本次性能评估的结论、原理、具体改动点与验证方式整理成可直接交给施工 AI 的说明书。
> 适用范围：`src/寒冬末日/界面同层版/界面/状态栏/` 下的 Vue/TS 代码。
> 症状：手机端在 LLM 流式输出期间整页卡顿、滚动/输入有掉帧，桌面端相对顺滑。
> 基调：**不改变业务语义**，只压缩每次流式 tick 的工作量与合成成本。

---

## 0. 结论 TL;DR

流式卡顿的根因是 **每 80 ms 一次的 `patchAssistantMessage('stream')` 周期**同时触发了以下连锁开销，手机中低端 CPU/GPU 撑不住：

1. 为当前楼层跑 **两次** `buildFinalHtml`（重的一条：`formatAsDisplayedMessage` + `createHTMLDocument` 全量 parse + 跨 iframe 宿主 DOM selector + `appendChatu8ArtifactsToHtml`）。
2. `syncTranscriptFlags(clipTranscriptItemsForUi([...]))` 每次都产出全新的条目对象数组，破坏 Vue diff 的引用相等，导致所有可见卡片都 patch。
3. `TranscriptList.itemsSignature` 的签名里包含 `len: item.content.length`，token 每来一次，签名就变，watcher 跑一次完整滚动锚定逻辑。
4. `TranscriptMessageCard` 的 watch 签名里包含完整 HTML 字符串，流式阶段每 tick 都在做 KB 级 join+比较；随后 `v-html` 整块子树替换 + `hydrateAssistantBodyImages` + `bindAssistantBodyInteractions`。
5. 顶栏、侧栏、底栏、FAB、图片按钮等 9 处 `backdrop-filter: blur(10~18px)`，流式滚动期间合成层反复重算。
6. `recordLifecycleTrace` / `debugConsoleLog` 的 payload 对象（含 `summarizeTranscriptForDebug(transcript.value)`）即使开关关闭也会在调用前构造。

**预期收益**：把 P0 全部做掉，手机端单次 patch 的 JS 耗时可下降 60% 以上；合成层降到可接受数量后，滚动能恢复流畅。

## 3. 优化措施（按优先级分组）

### 🔴 P0 — 必做，收益最大

---

#### P0-1 · 流式阶段不再调用两次 `buildFinalHtml`

**原理**：流式期间正文还在增长，用户看到的就是纯文本；`formatAsDisplayedMessage` + `appendChatu8ArtifactsToHtml` 这两条重管线不会带来可见差异（也不会有图片出现），完全可以延后到 `phase === 'done'` 时跑一次。

**改动文件**：`src/寒冬末日/界面同层版/界面/状态栏/useStreamingDemo.ts`

**改动位置**：`buildTranscriptItem`（约 1262 行）。

**改动前**：
```ts
const streamHtml = isDemoAssistant
  ? buildFinalHtml(renderSource, input.id, strippedRenderSource)
  : buildFinalHtml(displayRenderSource, input.id, strippedRenderSource);
const finalHtml = buildFinalHtml(displayRenderSource, input.id, strippedRenderSource);
```

**改动后**：
```ts
const isStreamingItem = isDemoAssistant && phase === 'stream';

// 流式期间：只产出轻量的 <pre> 文本；finalHtml 置空，stream 结束后再跑真正的渲染
const streamHtml = isStreamingItem
  ? buildStreamStageHtml(streamRenderSource, input.role, input.id)
  : buildFinalHtml(displayRenderSource, input.id, strippedRenderSource);

const finalHtml = isStreamingItem
  ? ''
  : buildFinalHtml(displayRenderSource, input.id, strippedRenderSource);
```

**注意事项**：
- `buildStreamStageHtml` 已经存在（约 231 行），沿用其逻辑即可。
- 一旦 `phase` 切到 `'done'`，原样走 `buildFinalHtml`，保证收尾渲染、图片 artifact 注入与原行为一致。
- 消费方 (`TranscriptMessageCard`) 已经根据 `item.isStreaming` 二选一，不需要改。

**预期效果**：每 tick 省掉 1 次 `formatAsDisplayedMessage`、1 次跨 iframe DOM 扫描、2 次 `createHTMLDocument` 全量 parse、若干正则替换。单 tick JS 耗时下降通常 50% 以上。

---

#### P0-2 · `TranscriptMessageCard` 流式分支走 `v-text`，不再走 `v-html`

**原理**：P0-1 之后 `streamHtml` 本身已经是 `<pre class="stream-stage-pre">{{escaped text}}</pre>`，完全没有真实 HTML 结构，不必让浏览器每 tick parse + 重建子树；用 `v-text` 就地更新文本节点，重排范围仅限 `<pre>`。另外流式阶段不会出现可交互图片，`hydrateAssistantBodyImages` / `bindAssistantBodyInteractions` 都不用跑。

**改动文件**：`src/寒冬末日/界面同层版/界面/状态栏/components/TranscriptMessageCard.vue`

**改动位置**：

1. 模板中流式分支（约 89 行）。
2. `assistantBodySignature` computed（约 141 行）。
3. watch(assistantBodySignature) 回调（约 250 行）。

**改动后（模板）**：
```vue
<!-- 流式阶段：只用 content / streamText，不需要 HTML 结构 -->
<pre
  v-if="item.isStreaming"
  ref="assistantBodyRef"
  class="assistant-body html-body is-stream-stage stream-stage-pre"
  :data-message-id="item.message_id"
>{{ streamDisplayText }}</pre>

<!-- eslint-disable-next-line vue/no-v-html -->
<div
  v-else
  ref="assistantBodyRef"
  class="assistant-body html-body"
  :data-message-id="item.message_id"
  v-html="item.finalHtml || '<p>(空回复)</p>'"
></div>
```

**改动后（script 片段）**：
```ts
const streamDisplayText = computed(() => {
  if (!props.item.isStreaming) return '';
  // item.content 是 extractStreamDemoContent 的结果，正是流式原文
  return String(props.item.content ?? '').trim() || '等待 token…';
});

const assistantBodySignature = computed(() => {
  if (props.item.role !== 'assistant') return `role:${props.item.role}:${props.item.message_id}`;
  if (props.item.isStreaming) {
    // 流式阶段不参与 v-html 重绑，签名只用于强制更新文本长度
    return `stream:${props.item.message_id}:${streamDisplayText.value.length}`;
  }
  const html = props.item.finalHtml;
  return `final:${props.item.message_id}:${props.item.phase}:${String(html ?? '').length}`;
});

watch(
  assistantBodySignature,
  async () => {
    if (props.item.role !== 'assistant') return;
    if (props.item.isStreaming) return; // 流式阶段不需要 hydrate/rebind
    recordComponentTrace('update');
    await nextTick();
    await hydrateAssistantBodyImages();
    await nextTick();
    bindAssistantBodyInteractions();
  },
  { immediate: true, flush: 'post' },
);
```

**注意事项**：
- 确认 `.stream-stage-pre` 样式在 `<pre>` 节点上工作正常（原来它落在 `<div class="assistant-body"> <pre>`，现在把类挂到 `<pre>` 本身；`theme-tokens.css` 和 `TranscriptMessageCard.vue` 原有 `:deep(.stream-stage-pre)` 规则仍然可以命中，但需要冒烟一下确认）。
- 进入 done 时，`isStreaming` 翻 false，watcher 会被触发一次，走正常 hydrate/rebind 路径。
- 如果需要用 `item.streamHtml` 作为 fallback（比如非 demo assistant 且处于 streaming 状态），可以把上面的 `streamDisplayText` 换成：
  ```ts
  return String(props.item.content ?? props.item.streamHtml ?? '').replace(/<[^>]+>/g, '').trim() || '等待 token…';
  ```

**预期效果**：
- 流式阶段每 tick 不再触发 `v-html` 子树重建、不再重绑图片事件。
- 手机端文本更新开销接近 "刷新一个 text node"。

#### P0-3 · `TranscriptList.itemsSignature` 去掉 `len` 字段

**原理**：这个签名的真实用途是"新增楼层时锚底 + 历史分页游标计算"。当前把 `content.length` 放进去，等于每 token 都会触发一次滚动锚定逻辑（`resolveTranscriptStartIndexOnItemsChange` + `nextTick` + 可能的 `scrollTop` 赋值），手机上尤其敏感。

**改动文件**：`src/寒冬末日/界面同层版/界面/状态栏/components/TranscriptList.vue`

**改动位置**：约 395 行的 `itemsSignature`。

**改动后**：
```ts
const itemsSignature = computed(() =>
  props.items.map(item => `${item.message_id}:${item.phase}`).join(','),
);
```

**注意事项**：
- `watch(itemsSignature, async (nextSignature, previousSignature) => { ... })` 里之前通过 `previousSignature?.map(...)` 拿 ids。签名改成字符串后要相应调整：
  ```ts
  watch(itemsSignature, async (next, prev) => {
    const previousIds = prev ? prev.split(',').map(entry => Number(entry.split(':')[0])).filter(Number.isFinite) : [];
    const nextIds = next ? next.split(',').map(entry => Number(entry.split(':')[0])).filter(Number.isFinite) : [];
    const appendedNewFloor = didTranscriptAppendNewFloor({ previousIds, nextIds });
    // 余下逻辑保持不变
  });
  ```
- 流式期间 `phase` 不变（一直是 `stream`），签名稳定；phase 切到 `done` 时签名变化一次，触发锚底。
- 新楼层插入时签名也会变化，锚底正常。

**预期效果**：流式期间不再反复进入滚动锚定分支，主线程负担 ↓。

---

#### P0-4 · `syncTranscriptFlags` 在 flag 未变时保持引用相等

**原理**：Vue 的 diff 严重依赖 props 引用相等。只要 `syncTranscriptFlags` 每次都产出新对象，`TranscriptList` 的所有可见卡片都会 patch；配合 P0-2 后卡片内 watcher 不再做重活，但组件级 patch 仍要走 vnode diff。让未变条目保留原引用即可让 diff 短路。

**改动文件**：`src/寒冬末日/界面同层版/界面/状态栏/useStreamingDemo.ts`

**改动位置**：约 2189 行 `syncTranscriptFlags`。

**改动后**：
```ts
function syncTranscriptFlags(items: TranscriptItem[]): TranscriptItem[] {
  const latestId = assistantMessageId.value;
  const isStreamingStatus = status.value === 'streaming';
  return items.map(item => {
    const nextIsLatest = latestId === item.message_id;
    const nextIsStreaming = nextIsLatest && (isStreamingStatus || item.phase === 'stream');
    if (item.isLatest === nextIsLatest && item.isStreaming === nextIsStreaming) {
      return item;
    }
    return { ...item, isLatest: nextIsLatest, isStreaming: nextIsStreaming };
  });
}
```

**注意事项**：
- 需要保证 `buildTranscriptItem` 返回的对象里，`isLatest` / `isStreaming` 字段值与此函数最终目标一致（目前已经一致）。
- 测试需确认 upsert 流程仍然能感知到 streaming → done 的状态切换（`phase` 变化会走 `buildTranscriptItem`，对象重建，引用自然变）。

**预期效果**：流式期间，历史楼层条目引用保持稳定，`TranscriptList` 的 v-for diff 基本只 patch 正在流式的那一条。

**改动文件**：优先放在 `theme-tokens.css`；如果有冲突，也可以在 `global.css` 末尾追加。

#### P1-6 · 流式期间跳过 `appendChatu8ArtifactsToHtml`

**原理**：这个函数负责把图片锚点注入到 HTML 中。流式期间图片还没生成、锚点也没写回消息层，等于空跑；而它内部要跨 iframe 查 5 个 selector、创建一次 HTMLDocument parse HTML、再扫描 img。

**改动文件**：`src/寒冬末日/界面同层版/界面/状态栏/useStreamingDemo.ts`

**改动位置**：`buildFinalHtml`（约 256 行）或 `applyTranscriptArtifacts` 的调用方。

**改动方案 A（推荐，最小侵入）**：
在 `buildFinalHtml` 内加一个轻量 fast path，由调用方传入一个 phase 提示：
```ts
function buildFinalHtml(
  renderSource: string,
  message_id: number,
  artifactSource?: string,
  options: { skipArtifacts?: boolean } = {},
): string {
  // ...原逻辑产出 html...
  if (options.skipArtifacts) return html;
  return applyTranscriptArtifacts({
    html,
    renderSource: artifactSource ?? renderSource,
    messageId: message_id,
    appendArtifacts: appendChatu8ArtifactsToHtml,
  });
}
```

再在 `buildTranscriptItem` 里 streaming 分支传 `{ skipArtifacts: true }`。如果已经做了 P0-1，这条基本已经自动生效，只是把 fast path 加在函数里，以防其他路径（比如未来新调用方）忘记判断。

**改动方案 B（更彻底）**：
给 `appendChatu8ArtifactsToHtml` 的开头加一个守卫：
```ts
function appendChatu8ArtifactsToHtml(html, renderSource, messageId) {
  // 流式期间正文极短且没有 prompt token，早退
  const promptTokens = collectChatu8PromptTokens(renderSource);
  if (promptTokens.length === 0 && !hasRenderedImagesInSource(renderSource)) {
    return html;
  }
  // ...原逻辑
}
```

二选一即可。

#### P1-7 · 调试日志惰性化

**原理**：`recordLifecycleTrace` / `debugConsoleLog` 在 `debugTraceRuntime.enabled === false` 时也会先把 payload 构造出来。流式热路径上的 `summarizeTranscriptForDebug(transcript.value)` 不仅是 map，还会 slice 预览文本。

**改动文件**：`src/寒冬末日/界面同层版/界面/状态栏/useStreamingDemo.ts`

**改动方案**（两种都做）：

1. 重构 `recordLifecycleTrace` 支持 lazy payload：
   ```ts
   function recordLifecycleTrace(
     scope: string,
     event: string,
     payload: Record<string, unknown> | (() => Record<string, unknown>) = {},
     traceId = resolveTraceId(scope),
   ) {
     if (!debugTraceRuntime.enabled) return null;
     const resolvedPayload = typeof payload === 'function' ? payload() : payload;
     const entry = recordDebugTrace(debugTraceRuntime, {
       traceId, scope, event,
       payload: { busy: busy.value, status: status.value, assistantMessageId: assistantMessageId.value, ...resolvedPayload },
     });
     if (entry) console.debug(`[stream-demo:debug] ${scope}.${event}`, entry);
     return entry;

     phase, sequence, messageId, nextSignature,

   }), traceId);
   ```

**注意事项**：
- 冷路径（opening 初始化、回退删除、生成结束等）不急着改，避免扩散修改面。
- `recordComponentDebugTrace` 在 `TranscriptMessageCard` 里每次 watch 都跑，可以直接加一层：
  ```ts
  function recordComponentTrace(event, payload = {}) {
    const runtime = (window as any).__STREAM_DEMO_DEBUG__;
    if (!runtime?.enabled) return;
    recordComponentDebugTrace({ scope: 'TranscriptMessageCard', event, payload: { ... } });
  }
  ```

**预期效果**：关闭调试时，流式 tick 中的隐性分配基本清零。

#### P1-8 · 流式节流自适应 + `requestAnimationFrame` 对齐

**原理**：80 ms ≈ 12.5 Hz 刷新，在低端手机（60 Hz 屏幕 + 弱 CPU）即便不卡顿也常错帧。适当放宽到 120~180 ms（视觉感知不明显）；更好的做法是用 `requestAnimationFrame` 聚合，让 UI 更新和屏幕刷新对齐。

**改动文件**：`src/寒冬末日/界面同层版/界面/状态栏/useStreamingDemo.ts`

**改动方案 A（最小改动）**：
```ts
const STREAM_TRANSCRIPT_PATCH_INTERVAL_MS = (() => {
  try {
    const cores = Number(navigator.hardwareConcurrency ?? 8);
    const isMobileLike = /Mobi|Android|iPhone|iPad/i.test(navigator.userAgent);
    if (isMobileLike || cores <= 4) return 160;
    return 80;
  } catch {
    return 80;
  }
})();
```

**改动方案 B（推荐，但要更仔细测试）**：
把 setTimeout 换成 rAF 聚合：
```ts
function queueNextStreamTranscriptPatch() {
  if (streamTranscriptPatchTimer || streamTranscriptPatchRunning) return;
  streamTranscriptPatchTimer = window.requestAnimationFrame(() => {
    streamTranscriptPatchTimer = 0;
    void flushScheduledStreamTranscriptPatch();
  });
}

function cancelScheduledStreamTranscriptPatch() {
  if (streamTranscriptPatchTimer) {
    window.cancelAnimationFrame(streamTranscriptPatchTimer);
    streamTranscriptPatchTimer = 0;
  }
  streamTranscriptPatchDirty = false;
}
```
> 注意 `streamTranscriptPatchTimer` 的类型变化（`number`）和取消方式。

**预期效果**：
- 每 patch 的合并窗口自适应到设备能力。
- rAF 方案能避免跨帧多次 repaint，滚动/打字输入更流畅。

## 3.5 施工边界约束（必须遵守）

以下约束来自当前 `界面同层版` 的真实运行链路，不能把本文件前面的 P0 当作纯渲染优化直接照抄落地。

### 3.5.1 `buildFinalHtml` 不是普通渲染函数

当前 `buildFinalHtml` 同时承担三层职责：

1. 调 `formatAsDisplayedMessage(renderSource, { message_id })`，应用酒馆宏、酒馆显示正则和最终 HTML 格式化。
2. 调 `normalizeDisplayedHtml`，清理 plugin-native placeholder 和局部 HTML 结构。
3. 调 `applyTranscriptArtifacts(... appendChatu8ArtifactsToHtml)`，把 chatu8 / plugin-native 图片 artifact 回填到 transcript HTML。

因此：

- **done 阶段必须保留 `buildFinalHtml`**，否则最终正文、图片 artifact、图片查看 / 重生交互会有丢失风险。
- stream 阶段如果要跳过完整 `buildFinalHtml`，也必须保留 `formatAsTavernRegexedString(..., 'display')` 或等价的显示正则效果；当前测试已经约束 streaming 不应暴露原始 regex / 运行时代码。
- 不允许把 `appendChatu8ArtifactsToHtml` 从 done / image-ready rebuild 路径移除。最多只能让流式 tick 不做跨 iframe DOM 扫描和图片 artifact 扫描。

### 3.5.2 plugin-native 图片是真相来源

当前同层 UI 的图片真相模型是 plugin-native：

- 正文原始消息里的 `image###...###` token；
- 宿主 / iframe DOM 中的 `.st-chatu8-image-span`、`.st-chatu8-image-container`；
- `message.extra.images`；
- `chatMetadata['st-chatu8']` 仅作为兼容 fallback。

施工边界：

- 不要重新引入 same-layer 自有图片持久化 manifest 或 `stream_demo.generated_images` 读写路径。
- 生图前必须确保宿主可被插件读取到目标楼层正文；当前通过 `ensureHostMesTextRendered(messageId)` 注入离屏 `.mes[mesid] .mes_text`，避免插件回退到 mesid 0。
- 插件图片完成后，应由 ready image mutation 触发局部 `refreshTranscriptItemsByIds(messageId)` 和 gallery revision；不要因为一次图片 mutation 重建全部 transcript。

### 3.5.3 done 后 MVU / lifecycle / 生图动作必须串行化

流式完成或被截断后，后续动作不是单一渲染：

1. `patchAssistantMessage('done')` 写最终正文。
2. `reprocessMessageVariablesById(..., { refreshMessage: true })` 触发 MVU 解析和变量写入。
3. `emitOfficialGenerationLifecycle(...)` 发 `MESSAGE_RECEIVED` / `GENERATION_ENDED` / `MESSAGE_UPDATED`，并确保宿主 `.mes_text` 可读，供 autoLLMClick / 插件链继续工作。
4. 插件原生生图完成后，可能继续写 `extra.images` / DOM，并反向刷新同层 UI。

当前已新增 `postDoneSideEffectsQueue.ts` 作为 post-done 副作用队列：

- 同一 `messageId` 的 post-done side effects 必须按 enqueue 顺序串行执行。
- 不同 `messageId` 的 side effects 可以并行，避免全局阻塞。
- 当前主流程通过 `runQueuedPostDoneAssistantSideEffects(...)` 把 done 后 MVU 重解析和官方 lifecycle emission 放入该队列；主程序只传入真实依赖（`reprocessMessageVariablesById`、`emitOfficialGenerationLifecycle`、`recordLifecycleTrace`），具体阶段顺序由独立模块负责。
- 当前主流程也通过 `runQueuedHostMessageUpdate(...)` 把同层版可控的宿主更新继续靠进同一队列：正文 `setChatMessages` commit、自动/手动生图触发前的宿主可见化和 `.mes_text` 预热、plugin-native 图片 ready 后的 transcript/gallery 刷新，至少同一 `messageId` 不再与 done 后 MVU/lifecycle 并发。
- 队列必须有 stage-aware timeout，防止同一 `messageId` 被永不 resolve 的副作用永久卡住。当前默认值：`mvu=45s`（MVU 通常 30s 内完成，预留余量）、`lifecycle=15s`、`host-message-update=30s`、`image-refresh=30s`、`auto-image=180s`（图片 LLM/插件链可能较慢，不能套短超时）、未知 stage 默认 `60s`。MVU / lifecycle 超时只记录 warning + lifecycle trace，并释放队列；不得把已完成正文直接改成 error。
- 尚未被同层队列完全收口的是酒馆官方 `saveMetadata -> saveChatConditional -> /api/chats/save` 自身的保存节奏；MCP 现场已观察到一次变量重处理会触发多次官方保存。若继续追 Windows JSON 写报错，下一步应评估是否需要宿主层 save/update gate 或官方 save debounce，而不是只继续加固同层 `patchQueue`。

### 3.5.4 截断不是错误态，必须单独判定

酒馆环境中 AI 输出可能因为 max tokens、手动停止、网络异常或 provider 行为而截断：

- 如果 `generate()` resolve 了部分文本，当前链路会把它当 done 文本进入 MVU reprocess。
- 如果 `generate()` reject，当前链路会写入 `生成失败：...`，不进入 MVU reprocess。

施工边界：

- 不要把“文本短 / 结尾突兀”简单当错误。
- 若要防止半截 MVU 命令污染变量，应在 done 后、MVU reprocess 前增加完整性判定，例如未闭合 `<UpdateVariable>`、JSON block、`[mvu_update]` 结构时跳过解析并提示重试。
- 此判定必须独立测试，不应混入 P0 渲染优化。

### 3.5.5 Windows 聊天 JSON 写入报错的边界

SillyTavern 本体曾出现 Windows `EPERM rename ...jsonl.<tmp> -> ...jsonl`，根因是 `write-file-atomic` final rename 遇到瞬时文件锁。当前本地 SillyTavern 已对 `tryWriteFileSync` 的 rename-stage `EPERM` / `EBUSY` / `EACCES` 做有限退避重试。

这不代表 same-layer 可以无节制制造并发写入：

- stream tick 应继续合并，不要每 token 直接写宿主聊天。
- done 后写正文、MVU、lifecycle、自动生图、图片回传刷新应按同一 messageId 串行收口。
- 如果继续追 Windows JSON 写入报错，优先看 post-done side effects 是否仍有绕过队列的 `setChatMessages` / `Mvu.replaceMvuData` / 插件原生写入。

### 3.5.6 runtime lease 不再用 chat 变量做 2 秒心跳

2026-05-11 现场验证确认：浏览器控制台里反复出现的
`Debounced metadata save cancelled` / `Saving metadata...` / `Saved metadata...` / `Chat Completions: saving token cache`
不是 same-layer UI 自己直接写文件，而是 SillyTavern 宿主在保存 chat metadata。
旧版 same-layer 的 `runtime_lease` 每 2 秒通过 `updateVariablesWith({ type: 'chat' })` 刷新一次 `stream_demo.runtime_lease.heartbeatAt`，会持续触发宿主 metadata save；关闭 same-layer UI 后保存循环消失，说明它是高频保存的触发源之一。

当前方案 A 已落地为“双通道租约”：

- `stream_demo.runtime_lease` 仍保留为持久恢复契约，只在 boot / active / suspended / closing 等状态边界写入 chat 变量。
- 2 秒活性心跳迁移到 `runtimeLeaseHeartbeat.ts`，写入 host/frame 可达 window 上的 `__edenSameLayerRuntimeHeartbeatStore`，不走 Tavern chat variables。
- `restoreHideState()` 读持久 lease 后，会用同 session/container 的 volatile heartbeat 判断当前 runtime 是否仍可恢复；只有 heartbeat 也 stale 时才执行宿主消息显隐恢复。
- 显式关闭、stale recovery、清理 hide state 时要同步清理 volatile heartbeat，避免下一次 bootstrap 误判旧 session 仍活着。

关键文件：

- `runtimeLeasePolicy.ts`：`SAME_LAYER_LEASE_HEARTBEAT_MS = 2_000` 只表示 volatile 心跳频率；持久 lease 不应按这个周期写 chat 变量。
- `runtimeLeasePersistence.ts`：只负责读写 / 清理 `stream_demo.runtime_lease`，以及 `isSameLayerRuntimeLeaseRecoverable(...)` 的恢复判定。
- `runtimeLeaseHeartbeat.ts`：只负责 `writeSameLayerRuntimeHeartbeat` / `readSameLayerRuntimeHeartbeat` / `clearSameLayerRuntimeHeartbeat`，不得引用 `updateVariablesWith`、`getVariables` 或 `replaceVariables`。
- `useStreamingDemo.ts`：`startRuntimeLeaseHeartbeat()` 只能调用 `writeRuntimeLeaseHeartbeat()`；不要把 interval 改回 `writeRuntimeLeaseStatus('active')`。

MCP / Playwright 业务现场验证锚点：

- URL：`http://127.0.0.1:8000/`
- 聊天：`末世寒冬 - 星穹秩序 - 2026-04-24@16h17m27s838ms.jsonl`
- 页面 iframe 正常显示 `EDEN-STAR / 楼层 / 最新 4-7 / 角色 / 画廊`。
- 静置 4.5 秒采样时，`getVariables({ type: 'chat' }).stream_demo.runtime_lease.heartbeatAt` 保持不变；同时 `window.__edenSameLayerRuntimeHeartbeatStore['container:0'].heartbeatAt` 正常跳动。
- 同一段 Playwright console 中不应再出现 `Debounced metadata save cancelled`、`Saving metadata...`、`Saved metadata...`、`token cache` 的 2 秒循环。

后续排查边界：

- `runtime_lease` 不是 Windows `EPERM rename` 的文件系统根因；根因仍是 SillyTavern 保存 `.jsonl` 时 final rename 遇到 Windows 锁 / 占用窗口。
- 旧版 2 秒 metadata save 会放大 rename 碰撞概率，因此属于高频触发器 / 放大器；当前方案已切掉 idle heartbeat 这条触发链。
- 如果方案 A 后仍出现 EPERM，应按真实业务写入分流：生成完成写正文、MVU 重处理、official lifecycle、plugin-native 图片回写、手动编辑消息，而不是继续怀疑 idle runtime heartbeat。

### 3.5.7 `StreamRenderer.vue` 流式预览组件的接入边界

2026-05-14 新增 `components/StreamRenderer.vue` + `streamRendererDisplay.ts`，作为流式阶段的独立预览组件，接入 `TranscriptMessageCard` 的 `item.isStreaming` 分支。设计决策与边界如下：

- **职责边界（模式 B）**：StreamRenderer 只负责 **流式阶段** 的轻量预览；`phase` 切到 `done` 后，`v-if` 翻到原 `finalHtml` 的 `v-html` 分支，完整管线（`buildFinalHtml` → `formatAsDisplayedMessage` → `appendChatu8ArtifactsToHtml` → 图片 hydrate / 交互 rebind）一律不变。不要让 StreamRenderer 承接 done 阶段渲染。
- **不自维护标签集**：StreamRenderer 不识别任何特定标签（不解析 `<scene>` / `<option>` / `<UpdateVariable>` / `<thinking>`）。结构化呈现（美化、折叠、按钮）一律交给酒馆 display 正则。`streamRendererDisplay.ts` 的 `buildStreamRendererHtml(message, role)` 只做三件事：① `applyRegexForDisplay(source, role)` 应用酒馆显示正则；② `stripVisibleChatu8PromptTokensHtml(...)` 防御性剥离 `image###` token（与 `TranscriptMessageCard` 原 `streamingAssistantHtml` computed 行为一致）；③ 正则结果为空时 `escapeHtml` 兜底。**不要在此恢复 `sanitizeAssistantRuntimeTagsForStreamingPreview` 那种 UI 侧标签美化。**
- **输入是快照不是 delta**：同层框架给的是响应式全量 `message` 快照（每 tick 整体重提供），不是 SSE 增量 chunk。组件用 `computed` 直接消费 `item.content`（即 `extractStreamDemoContent` 结果，就是流式原文），不要引入 buffer / chunk 切断防护 / blocks 数组那套增量解析。
- **image### 不在流式期出现**：依据 `开发文档.md` §9.5.1，`st-chatu8` 是两段式生图，`<image>` / `image###` token 是正文 `done` 之后插件二次 LLM 请求才补回的，不在正文流式 token 流里。StreamRenderer 内的 `stripVisibleChatu8PromptTokensHtml` 仅为与现有卡片行为一致的防御层，不是因为流式期真会出现 token。真正的图片 artifact 注入仍只在 done 阶段的 `appendChatu8ArtifactsToHtml`。
- **不跑 hydrate / rebind**：流式分支不再持有 `assistantBodyRef` 指向真实正文 DOM；`TranscriptMessageCard` 的 `assistantBodySignature` / `galleryEntrySignature` watcher 已经在 `isStreaming` 时早退，保持不变。StreamRenderer 不得在内部触发图片 hydrate 或插件按钮 rebind。
- **`useStreamingDemo.ts` 保持不动**：`buildStreamingPreviewHtml` / `streamHtml` 仍保留——`streamHtml` 是流式条目 `finalHtml` 的兜底（见 `buildTranscriptItem` 约 1646 行注释），`syncTranscriptFlags` 把"曾经最新"条目翻成非流式时要靠它。本次接入不裁剪 `useStreamingDemo.ts`，把 blast radius 限制在新增 2 文件 + `TranscriptMessageCard` 流式分支。
- **节流**：上游 `STREAM_TRANSCRIPT_PATCH_INTERVAL_MS`（桌面 80ms / 移动 160ms）已节流 `item.content` 的变化频率，`applyRegexForDisplay` 是字符串正则、远轻于 `formatAsDisplayedMessage`，故 StreamRenderer 不再自带二级缓存（`buildStreamingPreviewHtml` 原有的 `shouldRefreshStreamingPreview` 缓存仅服务它自己的 `streamHtml` 路径）。若 live 实测仍有 jank，再按 P1-8 评估二级节流。
- **打字机光标**：`active` 为真时在正文尾部渲染 `.stream-renderer__cursor` 闪烁块；CSS 用酒馆主题变量（`currentColor`），并在 `prefers-reduced-motion: reduce` 下关闭动画，与 P1-5 降级方向一致。

## 7. 风险提示

1. **流式 `finalHtml` 置空**：如果下游有地方在 streaming 期间读取 `finalHtml`（搜索 `item.finalHtml` 的所有用处），改造后可能拿到空串。目前确认：
   - `TranscriptMessageCard`：通过 `isStreaming` 走不同分支。
   - `TranscriptList` 等未直接读。
   - 若后续新增消费方，需给它加 `isStreaming` 判断或 fallback。
2. **`syncTranscriptFlags` 保留引用**：如果其它地方依赖"每次 rebuild 都产出新对象"来触发 Vue 响应式，需要确认没有 `shallowRef` 依赖（代码里没发现）。
3. **`backdrop-filter` 降级**：设计观感会变化，提前同步设计同学；桌面端不受影响。
4. **`requestAnimationFrame` 聚合**：如果宿主 iframe 因被 throttle（后台标签页）导致 rAF 停止，`streamText` 会短暂不更新。GENERATION_ENDED 时的 `flushScheduledStreamTranscriptPatch` 兜底能救，但建议测试后台切换场景。
5. **lazy payload 重构**：修改 `recordLifecycleTrace` 签名是广播式改动，请在同一次 commit 中一起改所有热点调用，避免半成品状态。
