# 界面同层版开发文档

## 1. 项目目标

`界面同层版` 位于 `src/寒冬末日/界面同层版/`，它以 `src/流式最小Demo/` 为业务基底，迁入 `docs/UI/`
的 UI/UX 组织方式，形成更适合移动端和同层 iframe 的流式阅读工作台。

其中，当前可参考与迁移的 UI 模板原型位于 `docs/UI/`。

本次迁移坚持两个原则：

1. **业务逻辑不改向**：`generate`、楼层写回、transcript 重建、开局 payload、回滚/重生成功能全部沿用原 Demo。
2. **壳层体验重构**：把 `docs/UI` 的顶栏、抽屉、弹窗、状态概览和 HUD 语气迁到 Vue 结构中。

## 4. 迁移策略说明

### 4.1 为什么不直接复制 `docs/UI` 代码

`docs/UI` 是 React + Tailwind + Vite 原型，而仓库目标项目是 Vue + Webpack +
iframe 运行形态。直接搬运会引入额外框架切换成本，并破坏现有业务代码稳定性。

因此本次采用：

- **业务层**：直接复制并沿用 `流式最小Demo`
- **视觉与交互层**：按 `docs/UI` 的模块拆法，用 Vue 重建等价壳层
- **样式层**：复用原 Demo 已整理好的 token / HUD 主题体系，再向 `docs/UI` 的层级组织靠拢

### 4.2 为什么把控制项塞进弹窗

同层 iframe 需要优先保证 transcript 阅读面积；移动端又要避免一屏内出现过多切换控件。因此：

- 主界面只保留摘要和高频动作
- 中低频设置收进弹窗
- 角色信息走侧抽屉

这比把所有开关都铺在顶部更适合长文本阅读。

## 6. 图片持久化方案（v2 - IndexedDB）

### 6.1 问题回顾

前几版实现都未能解决"iframe 重载后图片消失"的问题。根本原因链：

1. UI 在 iframe 中发起生图 → 插件识别为 **html-body 模式**
2. 插件把图片插入到 iframe 内的临时容器 `assistant-body-wrap`，而非宿主真实楼层的 `mes_text`
3. 插件的 `saveImageGroup` 落入 **chatMetadata 分支**（非持久化到消息层）
4. iframe 重载 → 临时容器消失 → 图片蒸发，只剩提示词占位

此外，早期版本尝试将 base64 图片数据直接存入聊天记录 JSON（`message.data.stream_demo.generated_images` 和 `message.extra.images`），导致聊天文件膨胀到 100M+，酒馆后台崩溃。

### 6.2 当前方案：生成后持久化桥接 + IndexedDB

核心思路：**不改变生成流程，不存 base64 到聊天 JSON，图片实体存浏览器 IndexedDB**。

#### 数据流

```text
插件返回 generate-image-response（含 base64 imageData）
                    ↓
    ┌───────────────────────────────────────┐
    │  persistGeneratedImageResponse()      │
    │  1. base64 存入 IndexedDB             │
    │     key = chatId:messageId:requestId  │
    │  2. 聊天 JSON 只存轻量引用：          │
    │     src = "idb://messageId/requestId" │
    │     （几十字节，不含图片数据）         │
    └───────────────────────────────────────┘
                    ↓
    setChatMessages() 写入 extra.images[swipeId]
    （聊天文件保持轻量）
                    ↓
    iframe 重载时：
    1. 从 extra.images 读到 idb:// 引用
    2. 从 IndexedDB 异步加载 base64
    3. 渲染图片
```

#### 关键模块

| 文件 | 职责 |
| ---- | ---- |
| `imageStore.ts` | IndexedDB 存取层。提供 `storeImage` / `loadImage` / `loadImagesByMessage` / `loadAllImagesForChat` |
| `imagePersistencePatch.ts` | 构建持久化补丁。`buildGeneratedImagePersistencePatch()` 不再写入 base64，改为写入 `idb://` 引用 |
| `generatedImageSourceResolver.ts` | 图片源解析。同步版 `readGeneratedImageSource()` 返回 `idb://` src；异步版 `readGeneratedImageSourceAsync()` 从 IndexedDB 加载真实图片 |
| `GeneratedImageAsset.vue` | 图片渲染组件。遇到 `idb://` src 时异步加载，加载前显示占位卡 |
| `transcriptImagePersistence.ts` | transcript 图片辅助层。负责正文 HTML 重建时重新拼接图片，以及把 `idb://` 图片异步替换成真实可显示 src |

#### idb:// 协议

自定义 URI 格式，用于标记图片存储在 IndexedDB：

```text
idb://{messageId}/{requestId}
```

- `buildIdbSrc(messageId, requestId)` — 构建
- `isIdbSrc(src)` — 判断
- `parseIdbSrc(src)` — 解析

#### 图片源解析优先级

`resolveGeneratedImageSource()` 的查询顺序（v2）：

1. **`extra.images[swipeId]`** — 持久化层（主要来源，含 `idb://` 引用）
2. **`chatMetadata['st-chatu8']`** — 插件缓存（只读兜底）
3. **`data.stream_demo.generated_images`** — 旧数据兼容

#### 存储特性

- **不跨设备**：IndexedDB 是浏览器本地存储，符合需求（"无需跨设备跨聊天档案"）
- **不膨胀聊天文件**：聊天 JSON 只存 `idb://` 引用字符串
- **iframe 重载安全**：IndexedDB 持久化不受 iframe 生命周期影响
- **同源共享**：iframe 与宿主同源，共享同一个 IndexedDB 实例

### 6.3 已废弃的方案

| 方案 | 废弃原因 |
| ---- | -------- |
| base64 存入 `data.stream_demo.generated_images` | 聊天 JSON 膨胀到 100M+，酒馆崩溃 |
| base64 存入 `extra.images[swipeId]` | 同上 |
| 桥接到插件 sec text 路线 | 插件找到的 `mes_text` 是 mesId=0（容器楼层），文本长度不足，退回 chatMetadata 分支 |
| 依赖 chatMetadata 持久化 | chatMetadata 中的图片在 iframe 重载后无法恢复 |

- **图片交互桥接调整**
  - 不再指望 `st-chatu8` 的通用 `ClickTrigger` 直接理解自定义画廊/正文恢复图。
  - `GeneratedImageAsset.vue` 改为组件级显式桥接：单击查看、双击重生、触摸长按查看。
  - `TranscriptMessageCard.vue` 会为正文恢复出的 inline 图补 `generated-image-hitarea`，保证点击目标不是裸 `IMG`。
  - `StoryPage.vue` 只负责把组件层事件转发到宿主原按钮 / 原图片节点，不再主导整条图片交互链。

- **正文重载恢复策略收敛**
  - 正文恢复不再混入 `chatMetadata` cache，只信 `extra.images` / 持久化层。
  - `extra.images[*].regex` 会映射为 `anchorText`，用于正文 inline 回插。
  - `plugin-native-data` 模式下，找不到锚点的图片不再整批 append 到正文文末；这些图片仍可在图廊查看。
  - `resolveIframeAssistantRoots()` / `resolveIframeMessageRoot()` 的查找范围已扩展到 `assistant-body-wrap`，兼容插件把原生按钮插进包裹层的情况。
  - 为绕过插件 placeholder 的“忽略首个直系 div 文本”逻辑，`assistant-body-wrap` 前增加了 sentinel div，避免正文主容器被整体排除。

- **正文图片渲染方式修正**
  - 正文恢复不再直接输出 `<img src="idb://...">`。
  - 改为先输出 `data-persisted-image-src`，再由 `TranscriptMessageCard.vue` 在挂载 / 更新后异步从 IndexedDB 解引用并填入真实 `src`，避免浏览器先渲染 broken image。

- **楼层变量瘦身**
  - `data.stream_demo.generated_images[*]` 新写入时不再持久化大段 `promptToken`。
  - 当前结构以 `requestId / imageId / src / alt` 为主，后续如需正文定位可继续补轻量 `anchorText / title / characterName`。
  - 旧楼层中已存在的 `promptToken` 不会自动清除；如需进一步减负，需要额外做一次清理迁移。

- **当前结论**
  - 图廊展示与交互链路已基本独立于 `ClickTrigger` 的 IMG 排除逻辑。
  - 正文重载恢复是否成功，当前主要取决于 `extra.images[*].regex` 与格式化正文之间的锚点命中质量。
  - 如果锚点完全失配，图片仍会只显示在图廊，不会强制堆到正文末尾。

## 9. 主修复方向（最新）

结合 `st-chatu8-debug-2026-03-18T08-36-14.txt` 与 `.tmp/system_simulator.decoded.html` 的现象对照，后续图片系统的**主修复方向**确定为：

- **正文内容与图片实体彻底分层**
- **正文只保存稳定 marker**
- **图片本体按独立 `imageId` / `requestId` 读取**

### 9.1 为什么要切到这条路线

当前已确认的问题是：

- 插件生图后，图片被插入到 iframe 内的 `assistant-body-wrap`
- `saveImageGroup` 最终落入 `chatMetadata` 分支
- iframe 一刷新，真实图片消失
- 只剩提示词或占位卡

这说明“把正文 DOM 当作图片真相源”本身就不稳定。

而 `.tmp/system_simulator.decoded.html` 中的“正文生图”模块采用了另一种更稳的模式：

- 正文中只保存 `<image>...</image>` 一类稳定标记
- 渲染时根据 `imageId / status / prompt` 单独加载图片
- 图片数据丢失时，也只退化为占位，不会破坏正文结构

### 9.2 后续目标结构

后续同层版图片系统应收敛为两层：

#### A. 正文层

- 只保留稳定 marker，不直接承载真实图片 data URL
- marker 至少应能关联：
  - `messageId`
  - `requestId`
  - `promptToken`
  - `imageId`（若插件侧可提供）

#### B. 图片层

- 按 `imageId / requestId` 单独读取图片实体
- 图片读取成功时显示真实图
- 图片读取失败时显示占位卡，但不丢 marker 和交互位置

### 9.3 这条路线解决什么问题

这条路线的目标不是“让临时插图看起来还在”，而是：

1. 避免把 iframe 临时 DOM 当成持久化来源
2. 避免刷新后真实图片整体蒸发
3. 保持正文中的图片位置稳定
4. 让图廊与正文共享同一套可恢复标识
5. 为“单击查看更多 / 双击重生图”提供稳定锚点

### 9.4 实施前置条件

在完全切到 marker 路线之前，仍需先保证：

- 正文双击的最终触发目标命中宿主真实 `mes_text`
- 不再把 iframe 的 `assistant-body-wrap / html-body` 当作插件保存目标

否则即使引入 marker，也仍会继续落入 `chatMetadata` 临时分支。
