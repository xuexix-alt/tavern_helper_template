# 寒冬末日｜界面同层版技术交接文档

> 文档性质：开发交接 / 技术总览  
> 目标读者：接手开发的程序员  
> 目标用途：帮助新接手者快速建立对 `src/寒冬末日/界面同层版/` 的系统认知，明确模块边界、核心链路、调试入口、风险点与后续改动切入点。

---

## 1. 项目摘要

`界面同层版` 是“寒冬末日”项目当前用于消息同层渲染的主工作台实现。它不是一个普通独立网页，而是：

- 运行在 **酒馆消息 iframe** 内的前端界面
- 以 **聊天消息、聊天变量、宿主插件行为** 为主要运行输入
- 以 `流式最小Demo` 为业务底座，在其上叠加寒冬末日项目的同层阅读壳、角色信息面板、图廊、opening 工作流和图片持久化恢复能力

当前系统的设计原则如下：

1. **业务逻辑优先复用现有链路**，避免重写生成、消息写回、opening、swipe、回退等基础能力
2. **UI 壳层与业务状态分离**，展示层尽量由组件承担，业务真相集中在 `useStreamingDemo.ts`
3. **图片系统不再信任 iframe 临时 DOM**，而是转向“消息层轻引用 + IndexedDB 实体层”的持久化方案
4. **宿主插件能力尽量桥接，不重复造轮子**，尤其是图片查看器与重新生成能力仍依赖宿主原节点

一句话概括：

> `界面同层版` = 流式消息工作台 + 同层阅读 UI + opening 工作流 + 图片持久化恢复 + 宿主桥接层。

## 2. 调试入口与运行前提

当前固定调试入口如下：

- **MCP URL**：`127.0.0.1:8000`
- **聊天记录**：`末世寒冬-星穹秩序`
- **渲染方式**：通过 **iframe 中的正则替换注入 UI 代码** 进行渲染

需要明确的运行前提：

- 本项目不是常规 SPA 调试模式，而是 **注入式渲染**
- UI 所在 iframe 与宿主酒馆页面之间存在大量 **跨容器 DOM/事件桥接**
- 调试时必须同时区分：
  - **消息层数据**
  - **聊天变量**
  - **iframe 内 UI DOM**
  - **宿主聊天楼层 DOM**

因此，任何“UI 看起来不对”的问题，未必是组件渲染问题，也可能是：

- 消息层未正确持久化
- 聊天变量未更新
- iframe 重建时数据未正确回注
- 宿主桥接目标未命中

## 6. 核心运行架构

### 6.1 挂载入口

入口文件为 `界面/状态栏/index.ts`。

职责：

- 在 `$(() => {})` 中启动应用
- 创建 Vue App
- 注入 Pinia
- 挂载到 `#app`
- 在 `pagehide` 时卸载

这说明它是前端界面项目，但运行时容器是 **酒馆消息 iframe**，不是普通网页。

### 6.2 页面壳

`App.vue` 负责：

- 外层主题与视觉容器
- 背景 / token / 全局壳样式承接
- 将主工作台交给 `StoryPage.vue`

它本身不承载核心业务判断。

### 6.3 页面编排中心

`pages/StoryPage.vue` 是当前 UI 的页面级控制中心，负责：

- 顶栏按钮区
- 左右抽屉（角色 / 图廊）
- transcript 主舞台
- 底部 dock / utility drawer
- setting / opening / detail 弹窗编排
- fullscreen 壳层行为
- 图片查看 / 重生图的宿主桥接

它既是页面编排器，也是部分跨容器交互桥接器。

### 6.4 业务中枢

`useStreamingDemo.ts` 是整个系统的主要业务中枢，负责：

- 聊天消息读取与 transcript 重建
- opening 工作流
- 普通输入生成与流式写回
- 删除回退、改词重生、assistant swipe
- reader state 与工作台日志
- 图片持久化与图片恢复
- 宿主事件监听与刷新调度

接手时请默认认为：

> **所有“真正的业务真相”优先在 `useStreamingDemo.ts`。**

组件层看到的状态，大多只是它输出后的消费结果。

## 8. 核心数据流

### 8.1 普通生成链路

```text
BottomComposer 提交输入
  → StoryPage.vue 调 useStreamingDemo.runDemo()
  → useStreamingDemo.runGenerationFlow()
  → createChatMessages(user)
  → createAssistantPlaceholder()
  → generate({ should_stream: true })
  → 监听 iframe stream token
  → patchAssistantMessage('stream')
  → 生成结束后 patchAssistantMessage('done')
  → reprocessMessageVariablesById()
  → rebuildTranscript()
```

关键点：

- assistant 楼层不是一次性写入，而是先建立 placeholder 再流式 patch
- transcript UI 始终围绕真实聊天消息重建，而不是只信本地内存状态

### 8.2 transcript 重建链路

```text
聊天消息变化 / 生成结束 / swipe / rollback / 外部事件
  → rebuildTranscript()
  → 读取聊天消息
  → buildTranscriptItem()
  → buildFinalHtml()
  → applyTranscriptArtifacts()
  → appendChatu8ArtifactsToHtml()
  → transcript / galleryEntries 更新
```

这是所有显示问题的核心排查入口。

### 8.3 opening 链路

```text
OpeningSetupPanel 更新 payload
  → useStreamingDemo 维护 openingPayload
  → shared/opening.ts 构建 opening prompt
  → generate()
  → 写回 opening seed / result message
  → opening payload 回写 chat variable
  → transcript 重建
```

### 8.4 图片持久化链路

当前图片系统采用：

> **消息层轻引用 + IndexedDB 图片实体**

链路如下：

```text
宿主插件返回 generate-image-response（含 imageData/base64）
  → useStreamingDemo 捕获结果
  → imageStore.storeImage() 存入 IndexedDB
  → 宿主原生链继续推进
     - chat[mesId].mes
     - extra.images[swipeId]
     - placeholder / 自动批量生图 / 按钮恢复
  → transcript 重建
  → generatedImageSourceResolver / transcriptImagePersistence 解引用
  → UI 内恢复显示图片
```

## 9. 图片系统专项说明

### 9.1 旧方案为什么失败

历史问题根因：

1. 图片生成后被宿主插件插入 iframe 临时 DOM
2. 插件保存路径落到 `chatMetadata`
3. iframe 重载后临时 DOM 消失，图片也跟着消失
4. 若把 base64 直接写入聊天 JSON，会导致聊天文件体积失控

结论：

- **不能把 iframe 临时 DOM 当图片真相源**
- **不能把大图 base64 直接写入消息 JSON**

### 9.2 当前设计

当前明确分为两层：

#### 成员层（消息层）

写入内容通常包括：

- `markerId`
- `imageId`
- `requestId`
- `promptToken`
- `anchorText`
- `idb://` 引用

#### 实体层（本地存储）

承载内容：

- base64 图片实体

承载位置：

- `IndexedDB / chatu8-ui-image-store`

### 9.3 图片相关关键文件

#### `imageStore.ts`

- IndexedDB 的打开、写入、读取、删除
- 图片实体存储层

#### `imagePersistencePatch.ts`

- 预热宿主正文与原生桥接
- 只读插件原生结果并投影到 same-layer
- 不再维护 UI 自己的图片真相层

#### `generatedImageSourceResolver.ts`

- 根据 `GeneratedImageRef` 解析图片来源
- 从消息层 / extra / cache 中找图
- 如果是 `idb://`，异步加载真实图

#### `transcriptImagePersistence.ts`

- transcript HTML 内持久化图片的辅助恢复与 hydrate

#### `GeneratedImageAsset.vue`

- 图片渲染组件
- 占位/恢复图统一入口
- 单击查看 / 双击重生图事件入口

#### `StoryPage.vue`

- 将 UI 内恢复的图片交互重新桥接回宿主原生节点

### 9.4 当前调试判断原则

图片问题排查时，优先按以下顺序问：

1. 消息层有没有正确写入引用？
2. IndexedDB 里有没有实体？
3. UI 恢复时有没有找到图片源？
4. UI 虽然显示了图，但交互有没有桥接到宿主原节点？

### 9.5 `st-chatu8` 原生图片链路兼容结论（2026-03-20 增补）

> 本节不是基于猜测，而是综合 `st-chatu8/` 混淆源码、混淆前关键文件、运行日志和还原文档整理出的**可直接用于修复同层 UI 的结论**。  
> 目标不是“介绍插件做了什么”，而是说明：**我们当前 UI 必须满足哪些原生假设，才能与宿主插件的后半段图片链路稳定协同。**

#### 9.5.1 `st-chatu8` 的正文生图不是单段流程，而是“两段式”

第一段：

```text
ClickTrigger / promptReq
→ getElContext
→ buildPromptForRequestType
→ llmRequest.LLM_IMAGE_GEN
→ parseImagesFromPrompt
→ insertImagesIntoElement
→ saveImageGroup
```

这一段做的是：

- 读取正文上下文
- 让 LLM 产出 `<images>/<image>` 标签文本
- 解析出 `regex / tag / prompt`
- 保存锚点组信息

第二段：

```text
taskQueue
→ autoLLMClick / placeholder
→ generate-image-request / response
→ createAndShowImage / triggerGeneration
```

这一段做的是：

- 真正的图片生成
- placeholder/按钮恢复
- 自动批量生图
- 原生图片结果回填

所以接手修复时必须区分：

- **前半段**：是“生成图片计划”
- **后半段**：才是“真的把图做出来并挂回消息”

如果你只修了前半段，看起来“保存成功”，后半段仍然可能断。

#### 9.5.2 原生保存分支不是只看 `html-body` / `mes_text`

`saveImageGroup` 的真实分支条件至少包括：

1. `insertOriginalText` 是否启用
2. 当前元素是否就是 `mes_text`
3. 当前元素若不是 `mes_text`，能否回查到外部真实 `mes_text`
4. 回查到的 `mes` 文本长度是否达到阈值（日志里能看到阈值 100）

因此同层版会出现一种很容易误判的情况：

```text
目标元素 = html-body
插件确实找到了外部 mes_text
但宿主正文长度过短
→ insertOriginalText 分支失败
→ 回退到 chatMetadata
```

这意味着：

- 同层 UI 不是“完全找不到宿主消息”
- 而是“找到了，但不满足原生正文改写的条件”

#### 9.5.3 原生聊天与同层 iframe 的第一持久化落点不同

原生 `mes_text` 成功分支：

```text
chat[mesId].mes
```

同层 `html-body` 常见回退分支：

```text
chatMetadata
```

但这只是前半段“落点”差异，不代表后半段消费层也一样。

#### 9.5.4 `extra.images` 才是后半段 placeholder / 自动批量生图更偏爱的消费层

这点必须单独记住：

- `chatMetadata` 是插件缓存层
- `image_groups` 是锚点中间态
- **`extra.images[swipeId]` 是 placeholder / 自动批量生图阶段的高优先级消费层**

日志里稳定出现：

```text
[iframe] Matched from chat[2].extra.images[0]
[iframe] Matched from chat[4].extra.images[0]
```

也就是说：

- 你只把图保在 `chatMetadata`
- 或只把锚点保在 `image_groups`

都不够。

如果后半段最终没有稳定落到 `extra.images`，原生 placeholder 链就容易失效。

#### 9.5.5 `image_groups -> extra.images` 迁移是真实存在的，不是推测

还原后的 `placeholder.js` 已经坐实这件事：

如果当前节点能回查到：

- `messageIndex`
- `context.chat[messageIndex]`
- `swipeId`

但当前 `extra.images[swipeId]` 没有对应内容，而 `generateElKey(rawText)` 又能在 `image_groups` 中找到一组保存过的图像记录，那么插件会执行迁移：

```text
image_groups[elKey]
→ chat[messageIndex].extra.images[swipeId]
→ delete image_groups[elKey]
→ saveChatConditional()
→ setcharData(...)
```

这条迁移对同层 UI 的意义是：

- 前半段落在 `chatMetadata / image_groups` 还不算结束
- 真正让原生后半段“认账”的，是后面能否迁进 `extra.images`

#### 9.5.6 `placeholder` 不是单纯显示层，而是“恢复 + 补按钮 + 触发生成”的半控制器

`placeholder.js` 直接依赖：

- `getItemImg`
- `getcharData / setcharData`
- `fuzzyMatchLine`
- `generateElKey / generateStableId`
- `createAndShowImage`
- `triggerGeneration`
- `showEditDialog`

这意味着 placeholder 会：

1. 在 DOM 中找图像锚点
2. 用 `rawText + nodeList` 重建位置
3. 必要时走模糊匹配兜底
4. 创建“生成图片”按钮
5. 有缓存时直接展示
6. 无缓存时主动触发生成
7. 长按时打开编辑

所以它不是一个“附带的小工具”，而是原生后半段的重要控制层。

#### 9.5.7 `rawText` / `nodeList` / “排除第一个直接 `<div>`” 是 placeholder 匹配成功的前提

`findAndReplaceInElement()` 会：

- 遍历所有文本节点
- 生成 `rawText`
- 生成节点位置映射表 `nodeList`
- 记录第一个直接 `<div>` 的文本范围
- 将这一段从匹配文本中剔除

所以只要同层版调整了：

- transcript 外层 DOM 包装
- 正文块层级
- 首个 `<div>` 的承载内容
- 逻辑文本顺序

就会直接影响：

- `fuzzyMatchLine`
- `insertPosition`
- placeholder 恢复
- 自动批量生图按钮补位

#### 9.5.8 `taskQueue` 是控制平面，不是显示状态

插件内部至少有这些状态：

- `queued`
- `running`
- `completed`
- `failed`
- `cancelled`

因此：

- 看到 `running` 不代表 UI 已经正确恢复
- 看到 `completed` 不代表图片已经被你的同层层级正确接住
- `cancelled` 说明插件主动放弃，不会再继续推进

修复时要把“任务状态”与“UI 显示状态”严格分离看待。

#### 9.5.9 `generate-image-request / response` 是独立的真实生图层

真正出图那层不是 `LLM_IMAGE_GEN`，而是：

```text
generate-image-request
generate-image-response
```

其中：

- `LLM_IMAGE_GEN`：生成 `<image>` 标签文本
- `generate-image-*`：真正请求图像生成器

从还原代码可以确认：

请求层至少维护：

```ts
imageGenerationQueue = new Map()
requestImageGeneration(prompt, negativePrompt, options)
getImageGenerationStatus(id)
```

响应消费层至少会读取：

- `success`
- `imageData`
- `error`
- `prompt`
- `change`
- `isVideo`
- `originalUrl`

这意味着：

- 我们如果后续要自己接“最终出图层”
- 最好直接面向这层桥接

而不是继续夹在前半段与 placeholder 后半段中间做半接半不接。

#### 9.5.10 `autoLLMClick` 是“生成结束后的二次触发器”

`autoLLMClick` 的职责不是简单自动点击，它更像：

```text
生成生命周期监听器
→ 判断 chat 长度 / swipe 数是否变化
→ 反查真实宿主 mes_text
→ 再次触发正文图片生成
```

也就是说，后半段原生链隐含依赖：

- 能观察到真实消息增长
- 能反查到真实宿主 `mes_text`

如果同层版只在 iframe 自己的 DOM 里成立，而不能回指宿主真实楼层，`autoLLMClick` 链就会断。

#### 9.5.11 对我们下一步修复最重要的两个选择

##### 方案 A：继续兼容原生完整链

那就必须满足这些前提：

1. 同层节点能稳定映射到真实消息 `messageIndex / mesId`
2. 宿主 `mes_text` 可被稳定找到
3. 宿主 `mes` 文本长度足够，不被持续回退到 `chatMetadata`
4. `rawText / nodeList / first div 排除逻辑` 不被新 UI 破坏
5. `image_groups -> extra.images` 迁移链能完整跑通
6. placeholder 能在当前 DOM 结构里正确补按钮

##### 方案 B：让同层 UI 完全接管后半段

那就要明确：

- 不再依赖原生 placeholder / 自动批量生图闭环
- 原生插件只保留：
  - 前半段 prompt 规划
  - 或最终真实生图接口
- 中间缓存与恢复完全改由我们控制

当前阶段如果只是想**先修稳定性**，建议优先选一个，不要混着修。

#### 9.5.12 下一步改代码时的直接检查清单

以后每次修图片链路前，先检查：

1. 当前点击目标是 `html-body` 还是 `mes_text`
2. 回查外部 `mes_text` 时得到的 `mesId / chatTextLength`
3. `saveImageGroup` 最终写到了哪里
4. `extra.images` 有没有真正出现
5. `image_groups` 有没有被成功迁走
6. placeholder 是否在反复 `re-processing`
7. taskQueue 当前是 `running / completed / failed / cancelled`
8. 真实 `generate-image-response` 是否回到了当前按钮

只要这 8 个检查点能稳定跑通，下一步修复就不会再是盲修。

## 11. 当前高风险点

### 11.1 `useStreamingDemo.ts` 过大

风险：

- 改动面极广
- 容易出现副作用
- 一个问题可能同时影响 transcript、opening、图片与刷新策略

建议：

- 小步修改
- 明确问题属于状态、渲染、持久化还是桥接

### 11.2 `StoryPage.vue` 同时承担页面编排与宿主桥接

风险：

- 表面是 UI 文件，实际包含宿主行为桥接逻辑
- 不适合在不了解宿主链路前直接大改

### 11.3 图片链路跨层过多

一次完整图片行为会跨过：

- 宿主插件响应
- `useStreamingDemo.ts`
- `imageStore.ts`
- `imagePersistencePatch.ts`
- `generatedImageSourceResolver.ts`
- `GeneratedImageAsset.vue`
- `StoryPage.vue`
- 宿主聊天 DOM

风险：

- 问题定位若只看单层，容易误判

### 11.4 正文锚点恢复脆弱

当前正文回插依赖：

- `anchorText`
- `promptToken`
- 正文文本命中质量

风险：

- 正文结构变化、正则替换变化、格式变化都可能导致图只剩 gallery 可见

### 11.5 iframe 运行边界

风险：

- `position: fixed`
- fullscreen
- 滚动容器
- 事件冒泡
- 宿主高度读取

这些都不是普通网页环境下的默认行为模型。

## 12. 已知事实与默认开发判断

接手时建议默认接受以下结论，不要回退到旧前提：

1. 不要再把 iframe 临时 DOM 当作图片真相源
2. 不要再把 base64 图片实体直接写进聊天 JSON
3. 图片实体层应继续以 IndexedDB 为主
4. 图廊是查看/恢复入口，不是图片唯一真相源
5. 图片相关行为最终仍要尽量命中宿主真实楼层节点
6. reader state 与 opening state 的真相在聊天变量，不在组件本地状态

## 17. 结语

接手 `界面同层版` 时，最容易犯的错误不是“不会写 Vue”，而是：

> 把它当成普通前端页面，或者把图片问题简化成单纯的 DOM 展示问题。

它本质上是一个：

- 运行在消息 iframe 内
- 依赖聊天消息与聊天变量
- 需要桥接宿主真实楼层与插件能力
- 同时还要维持本地恢复与持久化能力

的混合系统。

实际排查时，请始终先回答三个问题：

1. **真相源在哪一层？**
2. **当前坏的是状态、渲染、持久化，还是宿主桥接？**
3. **我改的是 UI 外观，还是跨层行为？**

只要这三个问题先分清，大部分接手成本都能显著下降。
