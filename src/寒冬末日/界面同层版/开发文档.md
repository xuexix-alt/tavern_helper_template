# 界面同层版开发文档

## 1. 项目目标

`界面同层版` 位于 `src/寒冬末日/界面同层版/`，它以 `src/流式最小Demo/` 为业务基底，迁入 `docs/UI/`
的 UI/UX 组织方式，形成更适合移动端和同层 iframe 的流式阅读工作台。

其中，当前可参考与迁移的 UI 模板原型位于 `docs/UI/`。

本次迁移坚持两个原则：

1. **业务逻辑不改向**：`generate`、楼层写回、transcript 重建、开局 payload、回滚/重生成功能全部沿用原 Demo。
2. **壳层体验重构**：把 `docs/UI` 的顶栏、抽屉、弹窗、状态概览和 HUD 语气迁到 Vue 结构中。

## 4. 迁移策略说明

### 4.1 为什么不直接复制 `docs/UI` 代码

`docs/UI` 是 React + Tailwind + Vite 原型，而仓库目标项目是 Vue + Webpack +
iframe 运行形态。直接搬运会引入额外框架切换成本，并破坏现有业务代码稳定性。

因此本次采用：

- **业务层**：直接复制并沿用 `流式最小Demo`
- **视觉与交互层**：按 `docs/UI` 的模块拆法，用 Vue 重建等价壳层
- **样式层**：复用原 Demo 已整理好的 token / HUD 主题体系，再向 `docs/UI` 的层级组织靠拢

### 4.2 为什么把控制项塞进弹窗

同层 iframe 需要优先保证 transcript 阅读面积；移动端又要避免一屏内出现过多切换控件。因此：

- 主界面只保留摘要和高频动作
- 中低频设置收进弹窗
- 角色信息走侧抽屉

这比把所有开关都铺在顶部更适合长文本阅读。

### 5.4 这轮联调确认的关键困难

#### 困难 1：触发目标容易落到 iframe 临时容器，而不是宿主真实楼层

用户提供的调试日志 `st-chatu8-debug-2026-03-18T08-36-14.txt` 已确认：

- 插件最终处理的根元素是 `DIV.assistant-body-wrap`
- 该元素位于 iframe 内
- 它不是宿主原楼层的 `mes_text`

这会导致插件把图片插入和保存逻辑建立在“临时容器”而不是“真实消息楼层”上。

#### 困难 2：插件虽然检测到 `insertOriginalText`，但最终仍退回原有 metadata 分支

同一份日志已确认：

- `insertOriginalText` 模式已启用
- 插件找到了一个 `mes_text`
- 但该 `mes_text` 的 `mesId = 0`
- 且 `mes` 文本长度只有 `9`
- 随后命中：
  - `mes 长度不足 - 退回原有逻辑`
  - `保存到 chatMetadata (非 mes_text)`

这意味着“看似生图成功”的那一轮，实际上并没有把图片保存到真实消息，而是保存到了 `chatMetadata`。

#### 困难 3：保存到 `chatMetadata` 只够短期显示，不够持久化

当前已观察到的实机现象：

- 生图返回后，正文末尾和图廊里能看到图片或提示词占位
- 一旦刷新 iframe / 重新挂载同层 UI
- 真实图片会消失，只剩提示词占位

这说明当前图像真相源仍停留在插件缓存 / `chatMetadata`，没有稳定沉到消息层。

#### 困难 4：图片交互链曾出现自触发递归

在本轮修复前，控制台曾出现：

- 多次 `start-task / mark-intent`
- `Maximum call stack size exceeded`

根因是：

- 找不到真正目标节点时，桥接逻辑退回点回当前 carrier 自己
- 于是同一张图再次命中 capture 处理器，形成递归

这一点已做第一轮收口，但仍需要继续验证是否完全消除。

### 5.5 当前阶段的真实结论

当前第一功能“图片持久化（画廊 + 正文载入）”不能视为完成。

更准确地说：

1. “正文双击 -> 原插件发起生图”已经跑通。
2. “插件把图片临时恢复到同层 iframe”已经跑通。
3. “图片被稳定保存到真实消息层，并能在 iframe 重载后继续恢复”还没有跑通。

目前最核心的问题已经从“能不能生图”收敛为：

- **必须确保插件生图 / 插图 / saveImageGroup 的目标最终落在宿主真实楼层的 `mes_text` 上**
- **不能再落到 iframe 的 `assistant-body-wrap / html-body` 这一类临时容器**

## 9. 主修复方向（最新）

结合 `st-chatu8-debug-2026-03-18T08-36-14.txt` 与 `.tmp/system_simulator.decoded.html` 的现象对照，后续图片系统的**主修复方向**确定为：

- **正文内容与图片实体彻底分层**
- **正文只保存稳定 marker**
- **图片本体按独立 `imageId` / `requestId` 读取**

### 9.1 为什么要切到这条路线

当前已确认的问题是：

- 插件生图后，图片被插入到 iframe 内的 `assistant-body-wrap`
- `saveImageGroup` 最终落入 `chatMetadata` 分支
- iframe 一刷新，真实图片消失
- 只剩提示词或占位卡

这说明“把正文 DOM 当作图片真相源”本身就不稳定。

而 `.tmp/system_simulator.decoded.html` 中的“正文生图”模块采用了另一种更稳的模式：

- 正文中只保存 `<image>...</image>` 一类稳定标记
- 渲染时根据 `imageId / status / prompt` 单独加载图片
- 图片数据丢失时，也只退化为占位，不会破坏正文结构

### 9.2 后续目标结构

后续同层版图片系统应收敛为两层：

#### A. 正文层

- 只保留稳定 marker，不直接承载真实图片 data URL
- marker 至少应能关联：
  - `messageId`
  - `requestId`
  - `promptToken`
  - `imageId`（若插件侧可提供）

#### B. 图片层

- 按 `imageId / requestId` 单独读取图片实体
- 图片读取成功时显示真实图
- 图片读取失败时显示占位卡，但不丢 marker 和交互位置

### 9.3 这条路线解决什么问题

这条路线的目标不是“让临时插图看起来还在”，而是：

1. 避免把 iframe 临时 DOM 当成持久化来源
2. 避免刷新后真实图片整体蒸发
3. 保持正文中的图片位置稳定
4. 让图廊与正文共享同一套可恢复标识
5. 为“单击查看更多 / 双击重生图”提供稳定锚点

### 9.4 实施前置条件

在完全切到 marker 路线之前，仍需先保证：

- 正文双击的最终触发目标命中宿主真实 `mes_text`
- 不再把 iframe 的 `assistant-body-wrap / html-body` 当作插件保存目标

否则即使引入 marker，也仍会继续落入 `chatMetadata` 临时分支。

### 9.5 当前开发判断

后续不再把“继续修 DOM 注入展示”当作主方向。  
主方向改为：

- **宿主真实楼层触发正确化**
- **正文 marker 化**
- **图片实体独立读取**

这将作为后续图片持久化与交互修复的默认设计前提。

### 9.6 已落地的第一轮实现

当前已经完成第一轮“图片实体独立读取”骨架：

- 新增 `generatedImageSourceResolver.ts`
  - 统一从以下三层解析图片实体：
    1. `data.stream_demo.generated_images`
    2. `extra.images`
    3. `st-chatu8` cache
- 新增共享组件 `components/GeneratedImageAsset.vue`
  - 正文和图廊统一改为使用该组件
  - 若能解析到图片实体，则直接渲染真实图
  - 若暂时解析不到，则退回占位卡
- `GeneratedImageRef` 已补充 `imageId`
  - 当前默认以 `requestId` 作为第一轮 `imageId`
  - 后续若能拿到插件更稳定的图片唯一标识，可平滑替换

这一轮实现的意义是：

- 即便插件没有把图重新插回正文 DOM
- 只要消息层里已经持久化了图片实体
- 同层版正文和图廊就有机会独立把图读出来，而不是永远只剩提示词占位
