> **日期**: 2026-03-20
> **项目**: 寒冬末日 - 界面同层版
> **状态**: 开发中（已按 2026-03-20 新日志做准确性校对）

## 1. 概述

本文档描述 `界面同层版` 项目中图片生成（生图）业务的当前实现方案。该模块负责：

1. 接收 LLM 生成的图片提示词
2. 将 base64 图片数据存储到 IndexedDB
3. 在消息层写入轻量级引用（`idb://` 协议）
4. 在 UI 中恢复显示图片
5. 处理图片交互（查看原图、重生图）

> **重要校对说明（2026-03-20）**  
> 本文档原先有一部分表述更接近“目标链路 / 设计意图”，但根据以下两份新日志复核：
>
> - `.tmp/插件日志/3月20日新的调试日志，LLM提示词被拦截.txt`
> - `.tmp/插件日志/3月20日新的控制台日志UI生图被拦截.txt`
>
> 可以确认：**当前实际运行中，UI 同层生图并没有稳定进入“宿主插件返回 generate-image-response → useStreamingDemo 捕获 → IndexedDB 持久化 → setChatMessages(extra.images)”这条理想链。**
>
> 当前更常见的真实路径是：
>
> ```text
> 同层 UI 元素（assistant-body-wrap / html-body）
> → st-chatu8 promptReq / LLM_IMAGE_GEN
> → parseImagesFromPrompt
> → insertImagesIntoElement
> → saveImageGroup
> → 保存到 chatMetadata（非 mes_text）
> ```
>
> 因此阅读本文时，请把下文分成两类：
>
> 1. **UI 层已经实现的目标持久化能力**
> 2. **当前日志实际观测到的插件原生运行路径**
>
> 两者目前**并未完全接通**。

### 1.1 设计原则

- **IndexedDB 持久化**：图片 base64 存储在浏览器本地 IndexedDB，不写入聊天 JSON
- **消息层轻引用**：`extra.images` 和 `data.stream_demo.generated_images` 仅存储引用
- **懒加载**：UI 仅在需要显示时才从 IndexedDB 读取真实图片数据
- **宿主桥接**：图片交互事件桥接回宿主插件处理

### 1.2 当前实测结论（基于 2026-03-20 新日志）

**已确认：**

1. 当前 UI 中的生图触发目标经常是：
   - `assistant-body-wrap`
   - `html-body`
   而不是宿主原生 `mes_text`

2. 插件当前实测会在这类目标上：
   - 进入 `promptReq.handlePromptRequest`
   - 调 `llmRequest.LLM_IMAGE_GEN`
   - 解析 `<images>/<image>`
   - 然后走：

```text
saveImageGroup → 保存到 chatMetadata (非 mes_text)
```

3. 在 2026-03-20 的新调试日志中，`saveImageGroup` 明确记录：

```text
insertOriginalText设置: false
分支: 保存到 chatMetadata (非 mes_text)
```

4. 因此，**当前实测路径并不是先写 `extra.images`，更不是先进入 UI 自己的 IndexedDB 持久化链。**

5. 也就是说：

```text
UI 的 IndexedDB 持久化能力 = 已实现的本地方案
插件当前实测路径 = 仍经常停留在 chatMetadata
```

这两层现在是并存的，不是完全统一的。

## 2. 核心模块职责

### 2.1 模块一览

| 文件 | 职责 |
|------|------|
| `imageStore.ts` | IndexedDB 图片实体存储层 |
| `imagePersistencePatch.ts` | 构造消息层轻引用 patch |
| `generatedImageSourceResolver.ts` | idb:// 引用解析为真实图片 |
| `transcriptImagePersistence.ts` | 正文 HTML 内图片 hydrate |
| `generatedImageActivation.ts` | 图片激活 payload 解析 |
| `generatedImageTriggerTarget.ts` | 图片交互目标选择 |
| `GeneratedImageAsset.vue` | 单图渲染组件/交互入口 |
| `useStreamingDemo.ts` | 图片链路中枢 (E. 图片链路) |

### 2.2 `imageStore.ts` - IndexedDB 存储

**数据库配置**：
- 数据库名：`chatu8-ui-image-store`
- 版本：1
- 对象仓库：`images`
- 索引：`chatId`, `messageId_chatId`

**存储记录结构** (`StoredImage`)：
```typescript
{
  key: string;           // `${chatId}:${messageId}:${requestId}`
  chatId: string;       // 当前聊天会话 ID
  messageId: number;    // 消息 ID
  requestId: string;    // 请求 ID（唯一标识）
  promptToken: string;   // 提示词 token
  prompt: string;       // 完整提示词
  imageData: string;     // base64 图片数据
  createdAt: number;    // 创建时间戳
}
```

**核心 API**：
- `storeImage(input)` - 存储图片到 IndexedDB
- `loadImage(messageId, requestId)` - 加载单张图片
- `loadImagesByMessage(messageId)` - 加载某消息的所有图片
- `loadAllImagesForChat()` - 加载当前聊天的所有图片
- `deleteImage(messageId, requestId)` - 删除图片

### 2.3 `imagePersistencePatch.ts` - 消息层补丁

**核心函数**：`buildGeneratedImagePersistencePatch()`

该函数构造消息层的持久化补丁，将图片引用写入：

1. **`data.stream_demo.generated_images`** - 流式演示生成的图片列表
2. **`extra.images[swipeId]`** - 每条消息的图片附件

**关键数据结构**：

```typescript
// 写入 stream_demo.generated_images 的条目
{
  markerId: string;      // 图片标记 ID
  imageId: string;       // 图片 ID
  requestId: string;     // 请求 ID
  promptToken: string;   // 提示词 token
  src: string;           // idb://messageId/requestId
  alt: string;           // alt 文本
  anchorText?: string;   // 正文锚点文本
  order: number;         // 序号
}

// 写入 extra.images[swipeId] 的条目
{
  markerId: string;
  imageId: string;
  requestId: string;
  request_id: string;
  promptToken: string;
  tag: string;           // prompt
  regex: string;         // anchorText
  src: string;          // idb://messageId/requestId
  alt: string;
}
```

**idb:// 协议格式**：
```
idb://{messageId}/{requestId}
```
例如：`idb://123/req-abc-456`

### 2.4 `generatedImageSourceResolver.ts` - 图片源解析

**职责**：根据图片引用解析出真实图片来源

**解析优先级**：
1. `message.data.stream_demo.generated_images` - 流式演示数据
2. `message.extra.images[swipeId]` - 消息附件
3. `chatMetadata['st-chatu8']` - 插件缓存
4. **IndexedDB** - 异步加载真实 base64

**关键函数**：
- `resolveGeneratedImageSource()` - 同步解析（优先从消息层）
- `readGeneratedImageSourceAsync()` - 异步解析（含 IndexedDB 读取）

**ResolvedImageSource 结构**：
```typescript
{
  markerId: string;
  imageId: string;
  requestId?: string;
  promptToken?: string;
  src: string;              // data:base64 | http:// | idb://
  alt: string;
  source: 'stream_demo' | 'extra' | 'cache' | 'idb';
}
```

### 2.5 `transcriptImagePersistence.ts` - 正文图片 hydrate

**职责**：将 `idb://` 引用的图片元素在 transcript HTML 中恢复

**核心函数**：
- `hydratePersistedImageElements()` - 批量 hydrate 图片元素

**流程**：
1. 查找所有 `src` 以 `idb://` 开头的 `<img>` 元素
2. 标记状态为 `loading`
3. 调用 `resolveSrc()` 解析真实 src
4. 更新状态为 `ready` 或 `missing`

### 2.6 `GeneratedImageAsset.vue` - 图片组件

**Props**：
```typescript
{
  entry: GeneratedImageRef;     // 图片引用
  variant?: 'inline' | 'gallery';  // 内联或图廊
  showCaption?: boolean;           // 显示标题
}
```

**Events**：
- `view` - 单击查看原图
- `regenerate` - 双击重生图

**手势识别**：
- 单击 → view
- 双击 → regenerate
- 长按（touch）→ regenerate

**payload 结构** (`GeneratedImageActivationPayload`)：
```typescript
{
  messageId: number | null;
  promptToken: string;
  requestId: string;
  imageSrc: string;
}
```

### 2.7 `generatedImageTriggerTarget.ts` - 交互目标选择

**职责**：在多种可能的交互目标中选择最合适的那个

**候选目标**：
```typescript
{
  hostButton: T | null;      // 宿主插件按钮
  hostImage: T | null;        // 宿主图片元素
  hostMessageRoot: T | null;  // 宿主消息根节点
  iframeButton: T | null;     // iframe 内按钮
  iframeImage: T | null;     // iframe 内图片
}
```

**选择策略**：
| 动作 | 优先级 |
|------|--------|
| `open` | hostImage → hostButton → hostMessageRoot → iframeButton → iframeImage |
| `regenerate` | hostButton → hostImage → hostMessageRoot → iframeButton → iframeImage |

## 3. 完整数据流

### 3.1 图片生成 → 存储 → 显示流程

> **注意**：以下流程描述的是当前 UI 层希望承接的“理想链路”。  
> 但从 2026-03-20 新日志看，当前实际运行并不总能进入这条链。

```
1. [宿主插件] 收到 LLM 生成的图片 base64
   ↓
2. [useStreamingDemo.ts] 捕获 generate-image-response
   ↓
3. [imageStore.ts] storeImage() 存入 IndexedDB
   ↓
4. [imagePersistencePatch.ts] buildGeneratedImagePersistencePatch()
   构造轻引用 patch（idb:// 协议）
   ↓
5. [useStreamingDemo.ts] setChatMessages() 写回消息层
   - data.stream_demo.generated_images
   - extra.images[swipeId]
   ↓
6. [useStreamingDemo.ts] rebuildTranscript() 重建 transcript
   ↓
7. [GeneratedImageAsset.vue] 渲染图片组件
   - 初始显示 placeholder
   ↓
8. [generatedImageSourceResolver.ts] 解析图片来源
   - 同步：stream_demo → extra → cache
   - 异步：loadImage() 从 IndexedDB 读取 base64
   ↓
9. [GeneratedImageAsset.vue] 更新显示真实图片
```

### 3.1.1 当前日志实测到的真实链路（2026-03-20）

根据新日志，当前更常见的是：

```text
ClickTrigger / promptReq
→ getElContext
→ buildPromptForRequestType
→ llmRequest.LLM_IMAGE_GEN
→ parseImagesFromPrompt
→ insertImagesIntoElement
→ saveImageGroup
→ 保存到 chatMetadata (非 mes_text)
```

关键日志证据：

```text
目标元素: assistant-body-wrap / html-body
...
insertOriginalText设置: false
...
分支: 保存到 chatMetadata (非 mes_text)
```

这说明：

- 当前被触发的是 `st-chatu8` 的前半段“图像标签规划链”
- 不是我们文档里“已经稳定接管的最终图片持久化链”

因此如果你发现：

- UI 文档说应该进 IndexedDB
- 但日志里只有 `saveImageGroup -> chatMetadata`

那不是矛盾，而是说明**当前 UI 和插件原生后半段还没真正打通**。

### 3.2 图片交互 → 宿主桥接流程


## 5. 当前实现与原始需求的差异

根据 `docs/重新开发指令和需求说明.txt` 开发时，以下为实际调整：

### 5.1 调整点 1：存储策略

**原方案（失败）**：
- 将 base64 直接写入聊天 JSON
- 问题：几张图片就 100MB，聊天文件体积失控

**当前方案**：
- base64 存 IndexedDB
- 消息层仅存 `idb://` 引用
- 优点：聊天 JSON 体积可控

### 5.2 调整点 2：UI 发起 vs 插件原生

**原需求**：
- UI 发起生图请求后，接管插件的存储和读取逻辑

**当前实现**：
- 插件对 UI 发起的请求仍按 `html-body` 模式处理（轻引用）
- UI 额外维护自己的 IndexedDB 存储
- 两套引用系统共存：`extra.images`（插件） + `IndexedDB`（UI）

**按 2026-03-20 新日志修正后的更准确表述**：

- 插件对 UI 发起的请求，当前实测仍经常按：

```text
html-body / assistant-body-wrap
→ 非 mes_text
→ saveImageGroup
→ chatMetadata
```

- UI 层虽然已经实现了自己的：
  - `imageStore.ts`
  - `imagePersistencePatch.ts`
  - `generatedImageSourceResolver.ts`
  - `useStreamingDemo.ts` 捕获 `generate-image-response`

  但**新日志没有证明这条链在当前问题场景里已稳定被触发。**

- 所以当前更准确的说法不是“两套引用系统共存且已协同”，而是：

```text
插件原生链：经常仍停在 chatMetadata
UI 自己的持久化链：已经实现，但当前场景下未稳定接管
```

### 5.3 调整点 3：持久化恢复链路

**问题**：
- iframe 重载后，插件对后续持久化缓存没有做处理
- 导致**重载失效**

**当前处理**：
- UI 在 `rebuildTranscript` 时主动重建图片引用
- 依赖 IndexedDB 中存储的实体恢复显示
- 仍存在的问题：插件侧的 `extra.images` 引用可能与 IndexedDB 不同步

## 6. 已知问题与风险

### 6.1 重载失效问题（未完全解决）

**现象**：
- iframe 重载后，图片无法恢复

**根因**：
- 插件对 UI iframe 发起的生图请求，按 `html-body` 模式处理
- 当前实测更常见的是插件写 `chatMetadata`，而不是稳定写 `extra.images`
- UI 的 IndexedDB 存储依赖 `useStreamingDemo` 捕获 `generate-image-response` 后手动写入
- 如果 iframe 在响应到达前重载，IndexedDB 中无数据

**当前缓解**：
- UI 层尽可能在 `rebuildTranscript` 时从 `extra.images` 恢复引用
- 也会尝试从其他引用层恢复
- 但如果当前场景里插件根本没走到 `generate-image-response → UI storeImage()`，那 IndexedDB 就不会有实体

**按新日志追加的更具体结论**：

当前问题场景下，真正阻断点更靠前：

```text
插件前半段只完成了 prompt / image tag / chatMetadata 保存
UI 后半段期待的 generate-image-response / IndexedDB storeImage 没有稳定出现
```

所以重载失效不只是“引用没恢复”，而是可能压根没有成功进入 UI 自己的实体存储阶段。

### 6.1.1 LLM 提示词被拦截 / 解析失败也是当前真实风险

从 `3月20日新的调试日志，LLM提示词被拦截.txt` 可确认两种真实失败样态：

#### 情况 A：LLM 请求失败

日志中明确出现：

```text
llmRequest.LLM_IMAGE_GEN
错误类型: Unknown
错误消息: ... upstream Google service exhausted its capacity ...
```

这时不会产生可用的 `<image>` 结果，更不会进入后续真实出图层。

#### 情况 B：LLM 成功，但返回内容格式不满足 `<images>/<image>` 约定

日志中也明确出现：

```text
未找到 <images> 容器 - 使用完整文本
找到 <image> 块: 0
解析完成，共 0 个有效图片
```

这说明当前另一个真实阻断点是：

```text
LLM 虽然回了内容
但回的不是插件期望的图像标签协议
→ parseImagesFromPrompt 得到 0 项
→ 后续整条链直接终止
```

所以现阶段“UI 生图被拦截”不止一种原因，至少包括：

1. LLM 上游服务失败
2. LLM 输出协议不符合 `<images>/<image>`
3. 输出协议正确，但保存落在 `chatMetadata`
4. 真实 `generate-image-response` 没有进入 UI 的 IndexedDB 链

### 6.2 正文锚点恢复脆弱

**依赖**：
- `anchorText` - 锚点文本
- `promptToken` - 提示词 token
- 正文文本命中质量

**风险**：
- 正文结构变化、正则替换变化、格式变化都可能导致图只剩 gallery 可见

### 6.3 双层引用系统

**当前状态**：
- 插件写 `extra.images`（`idb://` 引用）
- UI 写 IndexedDB（base64）+ `stream_demo.generated_images`（`idb://` 引用）

**问题**：
- 两套引用可能不一致
- IndexedDB 丢失时，`extra.images` 中的 `idb://` 引用指向空

## 7. 调试指南

### 7.1 四层观察面

| 层面 | 调试重点 |
|------|----------|
| **消息层** | `getChatMessages()` 中的 `extra.images` 和 `data.stream_demo.generated_images` |
| **IndexedDB** | `chatu8-ui-image-store` 数据库中的 `images` 对象仓库 |

### 7.2 调试判断原则

1. **消息层有没有正确写入引用？**
   - 检查 `extra.images` 和 `data.stream_demo.generated_images`

2. **IndexedDB 里有没有实体？**
   - 打开 DevTools → Application → IndexedDB → `chatu8-ui-image-store`

3. **UI 恢复时有没有找到图片源？**
   - 检查 `generatedImageSourceResolver` 输出

4. **图片交互有没有桥接到宿主原节点？**
   - 检查事件转发是否命中正确的宿主元素

### 7.3 按 2026-03-20 新日志补充的优先排查顺序

如果当前症状是“UI 生图被拦截 / 没出图 / 只留下插件日志”，先按这个顺序排：

1. **有没有成功返回 `<images>/<image>` 协议文本**
   - 看 `parseImagesFromPrompt`
   - 是否：
     - 找到 `<images>` 容器
     - 找到 `<image>` 块
     - 得到 `有效图片数 > 0`

2. **saveImageGroup 最终写到哪里**
   - 看是不是：
     - `chat[mesId].mes`
     - `extra.images`
     - `chatMetadata`

3. **有没有真正出现 `generate-image-response`**
   - 若没有，就说明还停在插件前半段

4. **UI 自己的 `storeImage()` 有没有执行**
   - 若没有，就说明 IndexedDB 方案根本没接管到这一轮

5. **重建 transcript 时是否有实体可解引用**
   - 没实体时，就算有 `idb://` 引用也没用

## 7.4 当前同层代码 vs 插件原生链的冲突清单（为什么这轮还停在 `chatMetadata`，没接进 UI 持久化链）

> 本节是基于**当前代码**与**2026-03-20 新日志**做的根因清单，不是修复方案。

### 冲突 1：UI 文档里的“理想链路”从阶段上就比插件当前实测链路更靠后

当前 UI 代码中的持久化入口是：

- `useStreamingDemo.ts`
  - `bindImagePersistenceEvents()`
  - `persistGeneratedImageResponse()`
  - `storeImage()`
  - `buildGeneratedImagePersistencePatch()`
  - `setChatMessages(...)`

它接的是：

```text
generate-image-request
```

而 2026-03-20 新日志显示，本轮实际只稳定走到了：


也就是说：

- **插件当前实测仍停在“图像标签规划 + 锚点保存”阶段**
- **UI 代码等待的是“真正出图响应”阶段**

这两段没接上，自然进不了 UI 的 IndexedDB 持久化链。

### 冲突 2：当前 UI 的图片持久化事件桥只在 `isOpeningWorkbenchHost` 为真时才会绑定

代码证据：`useStreamingDemo.ts`

```ts
const initialContainerMessageId = readCurrentContainerMessageId();
const isOpeningWorkbenchHost = initialContainerMessageId === 0;
...
onMounted(() => {
  ...
  if (isOpeningWorkbenchHost) {
    bindImagePersistenceEvents();
  }
});
```

也就是说：

```text
只有当前 iframe 所在容器 messageId === 0
才会监听 generate-image-request / generate-image-response
```

这会带来一个很强的前置条件：

- 如果这轮同层 UI 不是挂在 `messageId = 0` 的 opening/workbench 容器里
- 那么 UI 自己的图片持久化事件桥**压根不会启动**

日志证据是：两份 3 月 20 日日志里没有出现任何：

- `stream-demo:image-bridge`
- `request-received`
- `response-matched`
- `persist-begin`
- `idb-store-success`
- `persist-success`

这高度说明：**至少在本轮问题场景里，UI 的事件桥并没有真正接管到图片响应。**

### 冲突 3：插件当前触发目标不是宿主原生 `mes_text`，而是同层 DOM (`assistant-body-wrap` / `html-body`)

新日志里明确出现：

这说明当前同层交互发给插件时，插件收到的首先是：

- `assistant-body-wrap`
- `html-body`

而不是宿主原生：

- `mes_text`

所以插件当前分支容易走成：

```text
非 mes_text
→ saveImageGroup
→ chatMetadata
```

而 UI 代码后面期待的是：

```text
宿主图片生成完成
→ generate-image-response
→ persistGeneratedImageResponse
```

两边的“目标节点语义”还没统一。

### 冲突 4：当前日志里 `insertOriginalText` 被关闭或无法命中，导致插件前半段不会落进正文/extra 层

```text
insertOriginalText设置: false
```

- 也没有先进入一个更贴近宿主消息层的路径

- `data.stream_demo.generated_images`
- `extra.images[swipeId]`

当前实测里这一跳并没有稳定发生。

### 冲突 5：就算前半段成功解析出 `<image>`，也不代表后半段真实出图事件一定发生

3 月 20 日日志里存在两种情况：

#### 情况 A：解析出 0 张

```text
未找到 <images> 容器 - 使用完整文本
找到 <image> 块: 0
解析完成，共 0 个有效图片
```

这种情况下，后半段根本没有后续可走。

#### 情况 B：解析出 3 / 4 张，但仍只保存到 `chatMetadata`

```text
解析完成，共 4 个有效图片
...
分支: 保存到 chatMetadata (非 mes_text)
```

这说明：

- “解析成功” ≠ “真实图片请求已触发”
- “有 image tags” ≠ “UI 持久化链已接管”

当前 UI 文档原先有点把这两件事写得太近了。

### 冲突 6：UI 持久化链要求必须收到 `imageData`，而当前日志没证据显示这一步发生

`persistGeneratedImageResponse()` 的输入要求是：

```ts
{
  messageId,
  requestId,
  prompt,
  promptToken,
  imageData
}
```

而新日志只明确看到：

- `LLM_IMAGE_GEN` 返回 `<image>` 标签文本
- `saveImageGroup` 保存图像锚点

没有看到：

- `generate-image-response`
- `imageData`
- `storeImage()`
- `setChatMessages(data/extra patch)`

因此当前最直接的事实是：

```text
UI 的持久化链输入前提（imageData）尚未满足
```

没有 `imageData`，`imageStore.ts` 那套链就无从启动。

### 冲突 7：UI 的请求-响应匹配依赖 `messageId` 绑定，但当前插件前半段链并不天然提供这个绑定

UI 这边的桥接做法是：

- 在用户意图发生时：
  - `beginPendingImageTask(messageId)`
  - `markRecentImageIntent(messageId)`
- 收到 `generate-image-request` 时：
  - 用 `imagePendingTaskManager.registerRequest(payload)`
  - 必要时 fallback 到最近意图 / DOM 解析

这套机制的前提是：

```text
后半段真的发出了 generate-image-request
并且能把请求重新绑定回某个 messageId
```

但本轮日志里连 `generate-image-request` 都没有实证进入 UI 桥，所以：

- `imagePendingTaskManager`
- `persistGeneratedImageResponse`

这一整套绑定机制还没真正上场。

---

### 冲突 8：当前同层 UI 的“恢复层”已经实现，但“接管层”没稳定触发

当前代码在恢复层是完整的：

- `generatedImageSourceResolver.ts`
- `transcriptImagePersistence.ts`
- `GeneratedImageAsset.vue`
- `galleryCache.ts`

这些负责的是：

- 从 `stream_demo.generated_images / extra.images / cache / idb://` 解析图片
- 在 transcript/gallery 中显示

但恢复层要工作，前提是上游至少有一种引用已经稳定写入。

本轮实测显示，上游更常见的是：

```text
chatMetadata
```

而不是 UI 当前最想消费的：

- `data.stream_demo.generated_images`
- `extra.images`
- `idb://`

所以“显示层已经写好”不等于“当前链路能跑到显示层”。

---

### 冲突 9：当前文档对 `extra.images` 的表述此前偏理想化，需要明确成“目标层，不是当前稳定实测层”

这次修订后，应该按下面理解：

- `extra.images`：**后半段原生链的目标消费层**
- `image_groups`：中间态锚点缓存
- `chatMetadata`：插件当前实测经常停留的回退层
- `IndexedDB`：UI 自己实现好的实体层，但当前这轮没稳定接到

如果继续把 `extra.images` 写成“当前已经稳定落盘的主层”，会误导后续修复。

---

### 冲突 10：当前代码与日志之间最大的总体冲突

可以总结成一句话：

```text
当前同层 UI 已经实现了“收到真实图片响应后如何持久化和恢复”的完整方案，
但 2026-03-20 这轮真实运行中，插件链路更常在“image tag 解析 + chatMetadata 保存”阶段就停住，
没有稳定进入 UI 这套最终持久化方案。
```

---

### 7.4.1 这轮最可能的主断点优先级（按修复价值排序）

1. **`bindImagePersistenceEvents()` 根本没启用**
   - 因为 `isOpeningWorkbenchHost !== true`

2. **插件这轮根本没发出 `generate-image-request / response`**
   - 只走了前半段 LLM 图像标签规划

3. **触发目标是 `assistant-body-wrap/html-body`，不是真实 `mes_text`**
   - 导致原生保存路径更容易回退到 `chatMetadata`

4. **当前运行里 `insertOriginalText` 被关闭**
   - 进一步提高了回退到 `chatMetadata` 的概率

5. **即便图像标签解析成功，也没有证明真实图片实体进入了 UI 的 `storeImage()`**

这 5 条就是“为什么这轮还停在 `chatMetadata`，没有接进 UI 持久化链”的当前冲突清单。
