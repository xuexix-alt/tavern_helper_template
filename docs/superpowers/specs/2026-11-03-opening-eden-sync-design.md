# Opening 同步伊甸配置方案

日期：2026-11-03。用户已批准实施；实现与现场验证见同日验收报告。

已确认范围：标准默认值，可编辑初始配置；救亡和技术规则固定。沿用能力看板默认展示、点击编辑进入草稿的交互。

## 现状与问题

- 新伊甸由 `eden/model.ts`、`defaults.ts`、`worldbook.ts` 和 `runtime.ts` 管理，聊天专属世界书是正式配置来源。
- 系统页已有能力草稿、预览和确认保存；任务、技术页只展示当前任务、线索与成果。
- 寒冬内置 opening 仍要求填写 `shelter_ability_summary`，并通过 `opening.ts` 从旧能力文件生成默认文本。这条路径无法确定新等级、条件和授权范围。
- 运行时 opening 目前只同步 `[同层PRE]自定义开局上下文`；内置寒冬分支没有同等的生成前持久化步骤。
- `generatePreReply()` 已调用 `prepareEdenGeneration()`，普通生成、开局和重生共用此入口；但它只刷新已确认文档，不会自动把初始草稿变成正式配置。
- 世界变量初始末日天数是 -90，不能直接拿它代表玩家选择的灾后开局。
- Opening 面板和 runtime preset 同时被其他故事使用，不能给所有角色卡自动安装伊甸。

本轮已查看当前源码和已有设计文档。已连接酒馆页面进行只读检查，当前未发现已挂载的 opening 表单，不把源码分析当作现场界面验证。

## 方案比较

| 方案 | 行为 | 取舍 |
| --- | --- | --- |
| 共用伊甸配置，opening 确认后写入专属世界书（推荐） | 初始选择直接成为系统页正式数据 | 首轮 AI 和后续面板一致；需要完善初始时间、导入和失败重试 |
| Opening 只放跳转系统页的按钮 | 玩家先去系统页保存，再回来生成 | 实现较少，但开局配置分散，容易漏步骤 |
| Opening 保留独立文本能力配置 | 将摘要直接附到开局提示词 | 操作简单，但会与世界书、系统页产生多个来源 |

采用第一种。

## Opening 的界面

在寒冬开局的人物、时间地点之后，增加「伊甸初始配置」卡片：

- 顶部显示四级体系中的当前等级、状态、起始灾变天数和「编辑」按钮。
- 六组能力按当前等级展示；未解锁内容折叠。选了高等级也不会自动确认入队等特殊条件。
- 默认 1 级、运行、无外接房间、无已掌握失散技术，采用已发布的能力定义。
- 初始技术区显示「尚未掌握」或已选择的技术标签；任务区显示当前目标、当前可用线索和是否已经开始计时。
- 不展示救亡规则全文、技术树全文或任务文案编辑框。

点击「编辑」后，可修改本体初始等级、能力名称/效果/限制/所需等级/启用及特殊条件、授权房号，并选择初始已掌握技术。高级能力编辑使用折叠区，共用系统页编辑组件。选择技术不自动附送设备、人口、原料或生产体系。

起始天数使用明确的结构化值：负数为灾前，0 及以上为灾后。A 档默认 -90；B/C 档按现有“灾后一年获得伊甸、七天后开场”的设定默认第 372 天，可自行修改。现场核对后将草案中的第 3 天修正为第 372 天，并同步对应日历时间。档位默认值只在未修改时提供建议，不覆盖玩家已填内容。时间文字与起始天数在确认摘要中并列展示，不用自由文本或旧 MVU 默认值猜测计时阶段。

旧「庇护所能力」必填文本框在启用本方案的寒冬 opening 中移除；兼容宏 `shelter_ability_summary`、`庇护所能力变量` 如仍被模板引用，统一由本次正式配置生成摘要。旧答案只作为迁移参考保留，不自动解析或执行为能力。补充设定仍可叙述剧情，但不能绕过正式能力配置授予权限。

## 草稿、确认与首轮生成

1. 打开 opening：优先读取当前聊天已有正式伊甸文档；无文档时建立标准草稿。打开、切换选项和编辑均不写世界书。
2. 草稿持久化在当前聊天的 opening 设置空间，保留刷新后的填写结果；不改变角色卡默认配置，也不启用新模式。
3. 点击「预览开局配置」：展示本体等级、实际生效能力、未满足条件、授权房间、已掌握技术、当前任务、起始日和首次期限。可展开查看 AI 将读取的「当前伊甸」「当前救亡任务」「当前伊甸技术」摘要，不展示完整任务与技术规则。
4. 点击「确认配置并生成开局」：校验后，将伊甸正式文档与开局上下文一起保存到当前聊天世界书；等待读取确认，再启用新模式并同步必要初始 MVU 字段。
5. 沿用 `prepareEdenGeneration()` 刷新本次上下文，然后发出首轮模型请求。保持原有 assistant-only 流程，不额外创建 user 消息，不改写载体正文。
6. 首轮成功后，系统页直接展示同一正式文档，任务、技术页直接读取同一进度，无需再次初始化。

修改草稿、日期、聊天、绑定世界书或正式版本后，预览失效。已有正式配置但未修改时，生成复用已确认文档，不要求重复确认相同内容。已有剧情后重新打开 opening，不再允许用初始配置覆盖当前进度；能力修改和新增成果走现有系统入口。

## 初始技术与救亡结算

新增 `initialTechnologies` 作为文档中可选、缺省为空的结构化初始条件，使用农业/工业/气象分支和 lv0—5 的稳定编号。

- 初始已掌握技术参与「当前伊甸技术」和当前任务目标的判断，不自动推定拥有该分支所有低级技术。
- 初始技术不写入剧情成果账本，不生成虚假的源楼层或剧情证据，也不触发期限重置。
- 同一技术已在初始条件中存在，后续不能再以首次获得同项技术结算；首次建立对应自持生产体系仍可单独结算。
- 本轮不增加「初始生产体系」编辑，避免把选择技术等同于已经建成生产体系。
- 灾前确认，起算日为 0；灾后开局，起算日为选择的开局天数。后续超过 30 天停机和人工恢复规则保持既有逻辑。
- 已掌握农业 lv0 时，任务看板不再要求寻找同项技术；没有取得时展示当前农业 lv0 目标。隐藏未来线索的规则继续生效。
- 导入、重新打开、失败重试和重复生成均不重新起算救亡周期，不清空成果。

现有文档缺少此字段时按空列表兼容。共同维护任务与技术状态计算函数，避免 opening、系统页和 AI 条目各自判断一次。

## 世界书与同步边界

沿用当前六条伊甸条目和稳定 owner，不另建一套 opening 版能力书。保留 `[同层PRE]自定义开局上下文`，该条目仅保存身份、场景、持续剧情约束；不再包含另一份可独立授权的能力定义。

保存时先完成所有校验，捕获聊天 ID、绑定世界书和伊甸文档 revision；经过宿主共享队列，在一次 `updateWorldbookWith` 中合并六条伊甸条目与开局上下文。保留手机和其他非本功能条目，发现同名非本功能条目或版本冲突则拒绝覆盖。

世界书、聊天变量和 MVU 不具备跨接口事务，不宣称它们能原子提交。记录本次初始化的操作标识和配置指纹：

- 世界书写入失败：保留草稿，停止生成。
- 世界书已保存但标记/MVU 同步失败：明确显示已保存及失败阶段，重试完成剩余同步，不再新增 revision 或重置周期。
- 已保存但模型请求失败：回到可重试状态，保留正式配置，禁止用标准默认值覆盖。
- 等待期间聊天或绑定变化：停止后续步骤，不能在新聊天继续同步或生成。

首次生成前，确保载体楼层的起始末日天数与本次 context 一致；仅初始化当前新开局，不覆盖已有剧情楼层。AI 输出不能将初始配置反向覆盖为旧等级和任务机制。

## JSON 与其他故事

- 寒冬内置 opening 默认启用伊甸配置；「新的故事」和无显式声明的 runtime preset 不启用。
- runtime preset 增加可选的 `integrations.eden` 声明；寒冬表单转成 portable preset 时带上该声明，其他卡不依赖标题或 preset_id 猜测接入。
- 扩展后的完整导出包使用 version 2，在独立的伊甸扩展段保存可移植初始配置；继续读取旧 version 1 和裸 v2 preset。
- 导出仅包括能力设置、起始天数和初始技术，不包含 revision、savedAt、剧情成果、恢复记录、聊天 ID、楼层、指纹或运行计时缓存。
- 导入伊甸扩展仅装入当前聊天草稿，经过预览确认再写入世界书；不沿用旧导入流程的即时正式写入行为。
- 包含伊甸扩展但 preset 未声明接入时，导入前明确报错，不悄悄丢弃。旧 JSON 的能力文本保留为迁移参考，不能自动授予权限。
- 旧版不含伊甸扩展的通用 runtime opening 保持既有导入和同步行为。

## 验收与交付

1. 新开局从默认 1 级到编辑、预览、取消、刷新：未经确认不写世界书、不启用新模式。
2. 确认后首轮请求已包含正确的新条目，旧能力、旧任务奖励不混入；开局只新增一条 assistant 正文。
3. 灾前 -90、灾后第 372 天及自定义开局日、跨灾变、恰好 30 天和超过 30 天使用同一计时逻辑；灾前不后台扣健康。
4. 初始技术影响目标但不算新成果；重复取得拒绝结算，首次建成生产体系可独立结算。
5. 保存失败、部分同步失败、模型失败后重试：不重置计时、不重复保存、不丢草稿。
6. 多聊天切换、换绑、版本冲突、手机条目保留及已有剧情重新打开均有覆盖。
7. 新旧 JSON 往返可用；通用故事和未声明接入的其他角色卡不出现伊甸配置。
8. 真实 Vue 交互和移动宽度检查，通过 5500 在酒馆新测试聊天验证世界书、首轮提示词及系统看板一致性。
9. 用户批准方案后再实施；完成相关验证后按此前要求提交、push、等待构建并刷新 CDN，报告实际下载校验结果。

建议实施顺序：统一能力组件与初始技术模型 → opening 草稿和起始日 → 联合保存/失败重试 → JSON 兼容 → 酒馆验收与发布。
