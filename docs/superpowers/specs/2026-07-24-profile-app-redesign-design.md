# 伊甸终端档案 APP 改版设计

## 目标

档案 APP 用于展示并控制人物随正文、微信和 MVU 变化而产生的动态人设。固定世界书仍是不可覆盖的基线；AI 生成的动态档案自动写入聊天世界书，同时在档案页中留下可解释、可编辑、可恢复的版本记录。

## 界面结构

采用“人物列表 + 独立人物详情”两级结构。

人物列表只承担快速扫描：正文刷新进度、批量分析入口、失败重试、人物当前状态、最近变化摘要和更新时间。刷新设置折叠到次要入口，不再占据首屏。人物行使用完整宽度，避免固定 390px 手机壳内的双栏正文挤压。

人物详情分为四个视图：

- `变化`：本次动态人设变化、变化前后、原因和证据。
- `档案`：当前已应用的动态字段，可进入编辑模式并保存。
- `依据`：本轮使用的正文、微信、MVU 和固定档案引用。
- `分析`：面向玩家的结构化分析说明，以及模型提供时的原始 `reasoning_content` 和原始响应。

详情页显示当前版本、来源、更新时间和应用状态。玩家编辑保存会创建新的玩家版本并立即更新动态世界书；恢复上一版同样创建一个新版本，保留审计链。

## AI 请求与响应

Provider 增加任务模式，至少区分：

- `chat`：沿用微信聊天提示层和 `{ messages: [...] }` 契约。
- `structured`：不注入微信聊天系统提示和回复预填充，严格按调用方提供的 JSON 契约返回。

自定义 OpenAI-compatible Provider 提供详细响应，保留 `message.content` 和可选的 `message.reasoning_content`。酒馆 `generateRaw` 只能提供最终文本，因此正式档案契约必须包含面向玩家的 `analysisNarrative`，不能依赖供应商特有的 reasoning 字段。

档案正式输出增加：

- `analysisNarrative`：玩家可读的分析说明。
- `changes`：字段、变化前、变化后、原因和各自证据引用。
- 现有动态档案字段和全局 `evidenceRefs`。

解析失败时保存原始回传和错误，允许档案页显示失败详情，但不覆盖当前已应用档案或世界书。

## 数据与版本

`profileViews` 继续作为当前可复用档案的唯一读取入口，扩展保存：分析说明、变化列表、原始响应、reasoning、来源信息和有限版本历史。旧记录缺少新字段时按空值读取，不要求破坏性迁移。

版本历史最多保留最近 10 版。每版包含文档、玩家行动建议、分析与证据、来源类型（AI、玩家编辑或恢复）和保存时间。

广播和后续业务继续读取 `profileViews` 当前版本，不复制平行档案状态。下一次 AI 分析把当前版本作为 `previous` 输入。

## 状态与通知

档案状态扩展为清晰的可观察流程：`idle → refreshing → success/failed`。协调器每次状态、视图或版本发生变化时通知档案订阅者。

`PhoneAppServices` 增加 `watchProfiles`。人物列表和详情页订阅它并请求重绘，从而捕获自动刷新、人物刷新、失败、AI 回传和玩家保存。批量刷新返回逐人物结果，UI 不再把部分失败宣告为全部成功。

## 错误处理

- AI 网络错误、响应格式错误和写世界书错误分别保留可读错误。
- 单人物失败不影响其他人物完成。
- 解析失败保留原始响应，不推进微信增量锚点。
- 玩家保存或恢复时先校验会话和人物，再写世界书；写入失败不替换当前版本。
- `reasoning_content` 缺失是正常状态，UI 显示正式分析说明。

## Apple 风格约束

- 390px 手机壳默认单列，不依赖顶层浏览器 viewport 的媒体查询。
- 44px 最小触控区域，按下即时反馈，状态变化持续可见。
- 导航和控制克制，主要内容优先；设置作为次级 disclosure。
- 使用系统字体、0 字距、清晰字重和足够行高。
- 支持减少动态效果、减少透明度和高对比度偏好。

## 测试与验证

- Provider 测试：结构化模式不含微信提示层；详细响应保留 reasoning。
- 解析测试：合法变化与分析可解析；旧记录仍可读取。
- 协调器测试：AI 成功自动应用并产生版本；解析失败保留原始回传；通知覆盖 refreshing、success 和 failed。
- UI 测试：列表进入详情、四视图切换、编辑保存、恢复版本、失败后重绘和批量部分失败提示。
- 构建后在 `127.0.0.1:8000` 酒馆现场验证真实角色、真实档案 API、移动端 390px 和桌面视口。
