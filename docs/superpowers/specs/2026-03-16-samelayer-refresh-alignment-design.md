# 同层版刷新域对齐设计

## 背景

本次修复仅讨论 `src/寒冬末日/界面同层版`。

当前同层版的刷新职责分散在以下几处：

- `useStreamingDemo.ts` 负责 transcript、外部事件同步、hidden 策略、图像提示词持久化
- `mvuRoleStore.ts` 负责 MVU `stat_data` 读取与监听
- `MvuRolePanel.vue` 负责左侧变量来源楼层的枚举与切换
- `StoryPage.vue` 负责生图双击代理、图廊跳转与 UI 交互

现状问题不是“某个点没刷新”，而是“谁该刷新哪一块”没有统一边界，导致：

- 正文区、左侧变量区、右侧图廊彼此带有隐式耦合
- 楼层创建、变量更新、删除回退、生图回传这几条链路会互相误触发全量重建
- 左侧变量区在目标楼层没有稳定 `stat_data` 时会自动回退到 `latest`，容易误导
- MVU 初始化和额外分析阶段的短暂空窗，会被 UI 解释成“应该回退或补救”，增加误判风险

## 本次设计目标

### 1. 正文浏览与变量浏览解绑

- 正文区只受 transcript 楼层浏览控制
- 左侧变量区只受角色 tab 内部“变量来源楼层”控制
- 右侧图廊只关心图片所属楼层，不跟随正文滚动强制切换

### 2. 刷新域收口

统一把 UI 刷新拆成四个固定域：

- `transcript`：正文列表、楼层卡片、流式内容、swipe 状态
- `mvuSources`：可选的变量来源楼层列表
- `roleSidebar`：左侧角色与系统信息展示
- `gallery`：右侧图廊、正文中的已生成图片回填

所有事件只声明影响哪些刷新域，不再让各模块自行猜测是否“顺便全刷”。

### 3. MVU 只读，不做 UI 补救写回

同层版 UI 的职责是“实时、适时得到准确的变量数据并显示出来”，不是替 MVU 做初始化或修正。

因此：

- UI 只读 `Mvu.getMvuData({ type: 'message', message_id })`
- 目标楼层没有稳定 `stat_data` 时直接空态
- 不回退 `latest`
- 不保留旧快照冒充当前楼层
- 不因为 UI 取数触发 `reloadInitVar`、`replaceMvuData` 之类写操作

### 4. 图片能力继续复用 st-chatu8 原链路

图片生成与图片交互的真实执行者仍然是酒馆环境中的 `st-chatu8` 插件，不在同层版 UI 内重做一套。

同层版 UI 只做三件事：

- 把双击正文、双击已有图片等动作，准确路由到对应楼层原生消息节点的触发机制
- 在插件完成提示词生成、生图、图片回传后，把该楼层已经进入 chat 的图片同步展示出来
- 保留原图片交互逻辑，包括双击重生、单击查看同一 `mes` 文本对应的其他图片

右侧图廊只是“收集器”，不是图片真源：

- 图廊收集来自 chat 正文和插件缓存的已存在图片
- 图廊中的图片点击/双击，仍然要尽量代理回原楼层的图片节点或按钮
- 不在图廊里发明一套绕开原 chat 的独立图片状态机

## 用户确认过的硬规则

### 正文区

- UI 仅在首次加载时跳到最新
- UI 仅在用户主动按“回底”时跳到最新
- 其他任何刷新都不应强制跳回最新

### 左侧变量区

- 左侧变量显示楼层与用户当前浏览楼层解绑
- 变量来源楼层由角色 tab 内部左右切换控制
- 当前拿不到 `stat_data` 时直接显示空态，不回退到 `latest`
- 更彻底的做法是：只把“确认拿得到 `stat_data` 的楼层”放进来源列表

## 事件到刷新域矩阵

### 1. 创建楼层并获得回传内容

#### 流式生成中

- 刷新域：`transcript`
- 目的：更新流式 assistant 卡片内容
- 禁止：改动左侧变量来源、跳最新、全量重建图廊

#### 生成结束并落盘

- 刷新域：`transcript`
- 如果正文内新增了生图按钮、生成图、图片提示词持久化结果：追加刷新 `gallery`

#### 如果本次回复同时包含 MVU 变量指令

- 等待 MVU 实际更新结束事件
- 刷新域：`mvuSources + roleSidebar`
- 如果变量指令是通过“额外模型解析”附加写回正文末尾，还需要补刷该楼层的 `transcript`

### 2. 变量更新

变量更新分两种来源，但 UI 处理原则一致：

- 主 AI 在剧情生成时同步输出变量操作
- 额外模型解析后把变量指令写回当前楼层正文末尾

统一规则：

- 监听 `Mvu.events.VARIABLE_UPDATE_ENDED`
- 重算 `mvuSources`
- 若左侧当前正在查看的来源楼层就是该楼层，则刷新 `roleSidebar`
- 若变量更新同时改写了该楼层正文，再补刷 `transcript`
- 不跳最新

### 3. 楼层操作

包括：

- 删除楼层
- 回退删除
- 改词重生
- `MESSAGE_UPDATED`
- `MESSAGE_SWIPED`

统一规则：

- 先刷新 `transcript`
- 再重算 `mvuSources`
- 若左侧当前来源楼层已不存在或已无 `stat_data`，直接进入空态
- 若受影响楼层挂有图片，再刷新 `gallery`

### 4. 生图整条链

包括：

- 双击正文触发生图按钮
- 插件拿到指令
- LLM 回传提示词
- 发起生图
- 图片回传
- 双击已有图片重新生成

统一规则：

- 双击正文时，由 UI 把事件代理到对应楼层的原生消息触发节点，让 `st-chatu8` 按原 chat 逻辑生成提示词和图片
- 触发时不全量刷新，只记录对应楼层图片任务状态
- 提示词回传时只更新该楼层的图片局部状态，不在 UI 内自行生成图片
- 图片成功回传后，UI 从 chat 正文或插件缓存中重新采集该楼层图片，并刷新 `transcript + gallery`
- 图廊中的单击/双击也应尽量代理回原楼层图片节点，保留“单击查看同 mes 其他图、双击重生”的原交互语义
- 左侧变量区默认不参与，除非这条链明确伴随 `stat_data` 更新

## 拟修改的原逻辑

### 1. 去掉左侧变量读取失败时的 `latest` 回退

当前 `mvuRoleStore.ts` 在目标楼层取不到数据时，会尝试读取 `latest` 并把 `source` 标成 `latest`。

本次将改为：

- 目标楼层失败即空态
- `source` 只表示当前目标楼层状态，不再做“临时回退 latest”
- `isRetrying` 仅用于额外分析期间的短暂重试提示，不能挟带回退展示

这是一个明确改变原有行为的点，实施时需要单独校验左侧角色面板、系统面板、来源楼层文案是否仍然清晰。

### 2. 变量来源列表只展示可读 `stat_data` 楼层

当前 `MvuRolePanel.vue` 已经部分通过 `readMvuStatData(effectiveId).ok` 过滤来源楼层，但仍保留了默认 `latest` 项，并允许目标楼层不可读时在 store 中回退。

本次将改为：

- 来源列表只保留确认有 `stat_data` 的楼层
- 如果当前选中的来源楼层失效，转为空态，而不是自动切到 `latest`
- 文案明确显示“当前是第几项 / 总共几项 / 是否最新楼层”

### 3. 收口刷新入口

当前 `useStreamingDemo.ts` 里有多条会触发“外部同步”的路径：

- `handleHostRefreshEvent`
- `queueExternalSync`
- `rebuildTranscript`
- `queueHidePolicy`
- `queuePersistDisplayedImagePrompts`

本次将增加统一的“刷新域调度入口”，目标不是重写全部逻辑，而是把事件到刷新域的决策收口到一层，再由这层调用现有函数。

### 4. 保留现有图片代理思路，不改成 UI 自主生图

当前 `StoryPage.vue` 已经有一层“把正文区双击和图廊图片交互代理回宿主楼层节点”的逻辑，这个方向保留。

本次不会改成：

- UI 自己发 prompt 请求后直接在前端拼出一套独立图片流
- 图廊直接脱离宿主楼层执行重生
- UI 单方面维护一份与 chat 脱钩的图片真相

本次只会增强它的可靠性：

- 更准确地按 `messageId / requestId / promptToken / imageSrc` 定位原宿主节点
- 在图片落盘后按楼层定向刷新 `transcript + gallery`
- 保证图廊只是收集与转发，而不是替代宿主消息

## 可靠性要求

### 1. 不误触发 MVU 初始化

- UI 不调用 MVU 初始化类写接口
- UI 读取不到数据时只显示空态
- 任何补救都不能通过写回数据来“补出来”

### 2. 不误导用户

- 没有该楼层数据，就明确告诉用户“当前楼层无 `stat_data`”
- 不用旧数据冒充当前楼层
- 不用 `latest` 冒充目标楼层

### 3. 不打断用户阅读

- 除首次加载和“回底”外，不主动跳最新
- 楼层创建、变量更新、生图回传都只刷新对应域

### 4. 接受 iframe 级重载是正常机制

同层版运行在酒馆 iframe 中，关闭酒馆和切换当前聊天都会触发 iframe 重载。

因此本次方案默认把 iframe 重载视为“正常系统行为”，而不是异常：

- 不依赖前一次 iframe 的内存状态存活
- 同层版应尽量从聊天数据、MVU 数据和已持久化的 reader chat state 恢复当前界面
- 所有刷新策略都必须允许“整个 iframe 重新挂载后重新建立监听、重新计算来源楼层、重新采集图廊”

## 实施顺序

### 第一阶段

- 清理左侧变量区的 `latest` 回退
- 固定“来源楼层只展示可读楼层”的规则

### 第二阶段

- 给同层版增加统一刷新域调度入口
- 把消息事件、MVU 事件、图片事件分别映射到固定刷新域

### 第三阶段

- 校验生图链和楼层删除/回退链在新规则下是否仍能正确更新 transcript 与 gallery

## 风险与验证重点

### 风险 1

去掉 `latest` 回退后，左侧变量区可能更频繁出现空态。

这是预期变化，不算回归；关键是空态要表达准确，不让用户误会为“系统坏了”。

### 风险 2

来源楼层过滤过严，可能导致某些刚生成但尚未完成变量落盘的楼层暂时不在列表中。

这是可接受的，因为该设计优先保证“只展示确定可靠的数据”。

### 风险 3

刷新域收口后，如果事件矩阵漏项，可能出现 transcript、roleSidebar、gallery 中某一块不更新。

因此实施后必须重点验证以下链路：

- 正常生成一轮剧情
- 带变量指令的剧情生成
- 额外模型解析并写回变量指令
- 删除或回退一段楼层
- 双击正文触发生图
- 双击已有图片重新生成
- 图廊中单击图片查看同 mes 其他图
- 图廊中双击图片重生并确认动作仍回到原楼层链路

## 结论

本次修复不追求“哪里不稳补哪里”，而是要把同层版的刷新责任收成一套明确规则：

- 正文刷新看消息事件
- 变量刷新看 MVU 事件
- 图片刷新看图片事件
- 三者联动，但不互相冒充

同时把左侧变量区切换成“无数据即空态、只展示可靠来源楼层”的保守模式，降低误导和误初始化风险。
