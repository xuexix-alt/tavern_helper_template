## same-layer-pre 画廊 beta 实证补充：存图、引用复用、手势转接

这一轮 same-layer-pre 画廊 beta 的目标不是重新实现一套图片库，而是验证前端界面如何尽量复用 st-chatu8 插件已经写入酒馆原生聊天的图片真相。结论是：生成请求只负责拿结果；持久化、图片身份和既有手势都应尽量跟随插件原生链路。

### 1. 图片真相的推荐查找顺序

如果前端界面想在另一个 UI 位置复刻已有图片，不建议把 `imageData`、base64 或图片 Blob 再存进同层 DB。优先按下面顺序解析轻引用：

1. `chat[messageId].extra.images[swipeId]`
2. 消息正文里的 `image###...###` 或 `<image>...</image>` 标签
3. 插件的 `image_groups` / `chatMetadata['st-chatu8']` 后备缓存
4. 宿主聊天楼层 `.mes_text` 里的插件 DOM，例如 `button.image-tag-button`、`.st-chatu8-image-span`、`.st-chatu8-image-container img`

其中 `src` 只应作为当前渲染用的临时值，不应写入轻引用 key，也不应进入同层长期存储。轻引用可以只保存消息楼层、swipe、tag/link、requestId、imageId、prompt token hash 等身份字段。

示例：

```html
<span
  data-chatu8-image-ref
  data-message-id="13"
  data-swipe-id="0"
  data-image-tag="image###...###"
  data-link="image###...###">
</span>
```

渲染时再用 `messageId + swipeId + tag/link` 去原生来源解析，拿到已有 `src` 后显示一份 `<img>`。这样 UI 只保存几十字节引用，不复制图片体积。

### 2. 事件模型：定向刷新，不扫全聊天

beta 验证下来，前端界面可以把图片引用刷新拆成两段：

```ts
eventOn(tavern_events.MESSAGE_UPDATED, id => refreshImageRef(id));
eventOn(tavern_events.MESSAGE_EDITED, id => refreshImageRef(id));
eventOn(tavern_events.USER_MESSAGE_RENDERED, id => hydrateImageDom(id));
eventOn(tavern_events.CHARACTER_MESSAGE_RENDERED, (id, type) => hydrateImageDom(id));
```

`MESSAGE_UPDATED` / `MESSAGE_EDITED` 适合刷新 `extra.images`、正文 tag、缓存身份；`USER_MESSAGE_RENDERED` / `CHARACTER_MESSAGE_RENDERED` 适合在宿主 DOM 落图后再补一次 DOM 水合。画廊关闭时只记脏事件，打开画廊时再懒扫描；画廊打开期间收到渲染事件，可以短延迟二扫一次，等待插件把 `<img src>` 写进宿主 DOM。

### 3. 空占位和重复来源的处理

现场验证时，插件同一张图附近可能同时存在 prompt button、ready image span/container、正文 tag。它们不代表三张图，而是同一张图的不同阶段或不同身份面。

合并时建议：

- 用 `messageId + swipeId + requestId/imageId/tag/link/promptTokenHash` 组成轻 key。
- `lightKey` 不能包含 `data:image/...`、base64、blob 内容或 idb 图片体。
- 当同楼层已有可显示的宿主图片或 `extra.images` 图片时，正文 tag-only 条目只作为身份补充，不应在画廊里再显示为空占位。
- `host-dom` 里的空壳节点如果没有 tag/link/requestId/imageId/src 等身份信息，应忽略。

### 4. 手势不是图片本身继承来的

在 iframe 或同层 UI 里视觉复制一个 `<img>`，不会天然继承插件绑定在宿主 DOM 上的单击、双击、长按逻辑。插件的按钮和图片操作通常围绕以下身份运行：

- `.mes_text`
- `.mes[mesid]`
- `data-link`
- `data-image-tag`
- `extra.images`
- `image_groups`
- `button.image-tag-button`
- `.st-chatu8-image-span`
- `.st-chatu8-image-container img`

因此前端界面要么把事件代理回宿主原始元素，要么复刻足够的数据属性并让插件原生处理流程重新绑定。beta 里验证出的手势方向是：

- 对 prompt-only 引用，单击优先交回插件原生 prompt button，让 `triggerGeneration(button)` 这类插件逻辑自己处理。
- 对已经有 `src` 的图片，单击、双击、长按优先交回宿主原始图片节点或其最近的插件图片容器，而不是交给 prompt button。
- 当前 v2.7.7 成品图的“双击”是同一媒体节点上的两次 `click`；第二次 click 才会在 `dbclike === 'true'` 时进入 `triggerGeneration(button)`。不能用单个原生 `dblclick` 代替，`dispatchEvent()` 返回 true 也不等于插件业务回调已执行。
- 本轮 pre 桥接和 Beta 实测使用 1200ms 长按契约；只派发 620ms 左右的 `mousedown → mouseup` 会在桥接计时器到期前取消，因此不能触发编辑。当前混淆 bundle 文本不能直接证明这个数值，旧版可读化文件中的 500ms 仅作历史版本参考。
- 长按触发后，要吞掉释放时浏览器合成出来的下一次 click，否则会出现“长按后又触发单击/重生”的串线。
- 移动端长按/双击应优先依赖 `pointerdown/pointerup` 的触摸时序，再把已确认的第二次 `pointerup` 转成插件要求的 click-click 序列；不能假设手机合成的两次 `click` 或原生 `dblclick` 与 PC 鼠标一致。若 iframe 捕获层 `stopPropagation/preventDefault`，或事件只发生在 clone 图片上，宿主插件 handler 就收不到。

### 5. 常见坑位

- 不要在 console、日志面板或持久化字段里展开 `src: "data:image/png;base64,..."`，大图会让调试工具和 Codex 会话卡死。日志只记录 `kind/length/prefix` 这类摘要。
- 不要让 `Number(null)`、`Number('')` 落成楼层 `0`。缺少 message id 时应返回 `null`，再从最近的 `.mes[mesid]`、正文容器或轻引用补身份。
- 不要用全局聊天扫描作为常态路径。正常刷新应以本楼层事件为入口，只有打开画廊或人工刷新时才做窗口内扫描。
- 不要把 st-chatu8 的 `generate-image-response.imageData` 当作同层长期图片库。它适合当前展示或交给插件原生流程，长期真相仍应回到 `extra.images`、正文 tag、插件 cache 和宿主 DOM。

### 6. 分阶段标志不能混为一个图片 ID

当前 st-chatu8 v2.7.7 的生图链路至少有以下几层标志：

```text
LLM 指令：<images>/<image>、regex、tag
正文标签：image###...###、<image>...</image>
原生占位：button.image-tag-button、.st-chatu8-image-span
DOM 关联：data-link、data-image-tag、data-request-id
请求状态：data-loading="true"
事件关联：generate-image-request / generate-image-response 的 id
已生成媒体：.st-chatu8-image-container 下的 img/video
持久化：chat[mesId].extra.images[swipeId] / image_groups
缓存：getItemImg(tag)、getItemBlob、getMergedAndSortedImages
```

这些标志含义不同：`regex` 是正文定位锚点，`tag/link` 是逻辑图片身份或提示词，`requestId` 是 DOM/response 关联，`src` 只是当前媒体证据。

当前 `data-request-id` 是由 tag 经过 `generateStableId()` 派生的 tag-hash 标志，不包含 `messageId`、`mesid` 或 `swipeId`，所以不能单独当作全局唯一图片 ID。外部 UI 应使用：

```ts
messageId + swipeId + requestId
```

并保留 `regex`、`tag`、`link` 作为不同层级的回退身份。不要把 `regex` 缺失时的文本直接伪装成 `image###...###`，否则会把正文锚点误当成图片提示词。

v2.7.7 当前 bundle 没有 `data-stable-id` 和 `image-tag-placeholder`；如果接入代码仍兼容这两个名称，应明确标为旧版本兼容，不应优先使用。

画廊只消费已有图片时，推荐判断：

```text
宿主 .st-chatu8-image-span 下存在 img/video → 已生成，复制显示
宿主有 button/span 但没有媒体 → 占位，不主动请求
只有 extra.images 的 tag/link → 尝试插件缓存
只有 regex 或正文 image### token → 只记录图片意图
```
