# 寒冬末日：开局与庇护所变量化集成方案草案

> 状态：讨论稿 / 方案备忘录
> 目的：固化当前共识，避免后续设计时遗漏、冲突或重复造设定。
> 说明：本文只记录当前阶段的总体方案，不等于最终实现细节。

## 1. 方案目标

本方案希望同时解决以下问题：

- 把“开局表单”从一次性 prompt 填写器升级为“开局构筑编译器”。
- 把庇护所能力、扩展翼、DIY 能力槽从静态文案改为结构化变量。
- 让世界书只在需要时按 `ability_key` / `wing_key` 回调详细描述，避免提示词膨胀。
- 允许开局阶段进行有限的自由构筑，提高可玩性、多样性和重开价值。
- 在开局完成后把本局构筑封板，后续只允许线性升级/增强，避免剧情 OOC。
- 让 UI、后台脚本、MVU 变量、提示词体系都围绕同一份结构化状态工作。

## 2. 当前共识

### 2.1 总判断

- 不是“只把开局变量化”就够了。
- 最稳的方案是：
  - **开局构筑变量化**
  - **庇护所运行态变量化**
  - **世界书按关键字回调能力详情**
  - **脚本按变量驱动，而不是按等级硬编码驱动**

### 2.2 等级体系的定位

- 庇护所等级仍然保留。
- 但等级不再直接等于“当前生效能力列表”。
- 等级更适合作为：
  - 解锁池扩大条件
  - 装配上限/槽位上限条件
  - 高阶扩展翼/模块的进入门槛

### 2.3 开局的定位

- 开局不是直接生成一段 opening 文本。
- 开局首先是“本局构筑生成器”。
- 开局阶段应当完成：
  - 决定初始构筑模式
  - 生成/展示能力池
  - 玩家进行点数构筑
  - 可选启用 1 个 DIY 能力槽
  - 生成能力 call key、边界摘要、庇护所总述
  - 最终封板并持久化

### 2.4 已定稿的庇护所主树与摘要结构

以下内容已定：

- 庇护所主分支采用：`守 / 养 / 管 / 扩 / 行 / 慰`
- `限制` 正式移出分类，改为独立的 **约束协议层**
- IMP 的定位升级为：
  - **总维持值**来源
  - 升级/演化判定的重要条件之一
  - 开局 `X point` 的判定参考之一
- 庇护所总述当前采用四段式：
  - 运行态
  - 可执行
  - 不可执行
  - 动力来源

说明：四段式总述先作为占位结构，后续如有更优表达方式可再迭代。

## 3. 世界书触发方式共识

### 3.1 基本认知

- 蓝灯：常驻激活，无关键字要求。
- 绿灯：条件触发，需要关键字。
- 因此，庇护所能力详情不适合全部常驻塞进上下文。
- 适合改造为“按 key 回调”的绿灯条目。

### 3.2 目标形态

- 世界书中保留静态蓝图数据。
- 每个能力/模块/扩展翼都拥有稳定 key。
- 提示词侧只注入 call key，而不注入整段能力全文。

示意：

```text
【【ability:safe.sealed_bulkhead】】
【【ability:survive.clinic_pod_t0】】
【【wing:medical.base】】
【【wing_module:medical.auto_doctor_t1】】
```

### 3.3 DIY 能力的特殊性

- DIY 能力不适合直接写回静态世界书文件。
- DIY 能力建议走动态注入：
  - `injectPrompts`
  - 或编译摘要层输出的动态 prompt block

## 4. 三层架构

当前方案按三层组织：

- 蓝图层
- 变量层
- 编译摘要层

### 4.1 蓝图层

蓝图层负责定义“可供构筑的静态资源”。

#### 蓝图层职责

- 定义能力注册表
- 定义扩展翼注册表
- 定义模块注册表
- 定义等级解锁池
- 定义能力包/流派包
- 定义依赖、互斥、cost、边界、标签

#### 蓝图层现阶段基础

- 现有 `庇护所升级能力.txt` 已具备 source of truth 倾向。
- 未来可从“能力总表”演进为：
  - 能力注册表
  - 扩展翼注册表
  - 模块注册表
  - 等级解锁表
  - build 包定义

#### 蓝图层要求

蓝图层需要满足：

- 可编辑
- 可写入运行时覆盖
- 可持久化引用

#### 关于“可编辑、可写、持久化”的当前共识

- 不建议运行时直接频繁修改仓库中的世界书文件。
- 更稳的方式是：
  - 静态蓝图留在仓库/世界书中
  - 动态覆写写入 `chat` 变量
  - 编译时把覆写合并进本局 build

### 4.2 变量层

变量层负责记录“本局真正生效的庇护所状态”。

#### 变量层分两部分

- `chat` 变量：
  - 开局构筑草稿
  - roll 结果
  - 点数分配
  - DIY 草稿
  - UI/事件辅助元信息

- `stat_data`：
  - AI 每轮读取的正式运行态
  - 当前已装配能力
  - 当前扩展翼状态
  - 当前约束边界摘要

#### 当前推荐分工

- `chat` 变量用于“编辑器态 / 构筑态 / 工作流态”。
- `stat_data` 用于“叙事态 / 运行态 / 稳定读取态”。

### 4.3 编译摘要层

编译摘要层不保存“真相”，只保存：

- 给 AI 用的摘要
- 给 UI 用的摘要
- 给世界书回调用的 key 列表

#### 编译摘要层职责

- 输出能力 call keys
- 输出扩展翼 call keys
- 输出 DIY 动态 prompt blocks
- 输出庇护所能力总述
- 输出构筑摘要
- 输出边界/限制摘要

#### 编译摘要层的价值

- 平时上下文只放摘要，节约 token。
- 只有需要细节时，才按 key 回调对应世界书条目。

## 5. 开局构筑方案

### 5.1 开局分四步

#### 第一步：确定构筑模式

候选模式：

- 默认升级
- 点数构筑
- 点数构筑 + DIY

此外，开局还应提供“世界观配置档位”选择，用于决定本局的外部环境压力、社会残存度、威胁构成与推荐流派方向。

#### 第二步：生成能力池

- 按起始等级决定基础可见池。
- 可叠加主题流派/能力包偏置。
- 不展示全量能力库，只展示本局允许池。

#### 第三步：玩家构筑

##### 方案 A：点数构筑

- 开局给予 `X` 点 point。
- 能力按等级/稀有度/类型拥有不同 cost。
- 玩家在允许池中进行有条件排列组合。

##### 方案 B：1 槽位 DIY

- 开局能力池保留为基础。
- 额外开放 1 个 DIY 能力槽。
- DIY 必须至少填写：
  - 命名
  - 描述
  - 边界
  - 分类
  - cost

#### 第四步：封板

- 开局完成后，build 写入变量。
- 构筑状态切为 `已封板`。
- 后续剧情仅允许线性增强，不允许随意重洗 build。

## 6. 线性变化原则

### 6.1 为什么需要线性变化

- 防止中途能力洗牌导致剧情理解崩坏。
- 防止 AI 在中后期无依据地改写庇护所能力边界。
- 保持玩家对本局 build 的稳定预期。

### 6.2 当前线性变化共识

- 开局后不允许随意移除核心能力。
- 后续变化主要允许：
  - `locked -> unlocked`
  - `unlocked -> equipped`
  - `tier 1 -> tier 2`
  - 边界摘要做小幅修正/补充
- DIY 槽默认开局后锁死，不允许中途重写。
- 若未来开放替换，只能通过重大剧情事件进行极少量调整。

## 6.5 流派与主分支关系

当前共识：

- `守 / 养 / 管 / 扩 / 行 / 慰` 是 **主分支 / 权柄树**
- “流派”是这些主分支的组合路线，而不是与主分支并列的新分类

当前建议的主流派方向：

- 守流：以战斗、防御、压制、征服为爽点
- 养流：以极端环境下的人口存活、维持、后勤、种田为爽点
- 管流：以秩序建立、社会治理、分配、博弈为爽点
- `扩 / 行 / 慰` 更多作为满足多样乐趣的辅助向分支，不单独作为最初主流派核心

## 6.6 IMP 元动力共识

当前已明确：

- IMP 不再只是关系数值的剧情说明
- IMP 应成为庇护所真正维持运转的“元动力”

建议的职责拆分：

- IMP 提供 **总维持值**
- 总维持值决定：
  - 哪些功能可稳定常驻
  - 哪些能力只能短时启动
  - 哪些升级/扩展可被解锁
  - 当前 build 是否有足够动力支撑

## 6.7 约束协议层共识

当前已明确：

- `限制` 不再作为一类能力
- 约束协议层是整个伊甸系统的高优先级边界总线

建议它至少负责：

- 越权拒绝规则
- 负载不足时的降级规则
- 外溢代价规则
- 维护成本规则
- 扩张前置条件
- 可替代方案模板

## 7. 当前推荐的数据组织思路

### 7.1 chat 变量侧

建议存在：

- `eden.opening.shelter_build`
- `eden.blueprint_overlay.custom_abilities`
- `eden.blueprint_overlay.custom_wings`

用途：

- 保存开局构筑草稿
- 保存蓝图覆盖层
- 保存 roll / point / DIY 配置

### 7.2 stat_data 侧

建议存在：

- `庇护所.已解锁能力`
- `庇护所.当前装配能力`
- `庇护所.扩展翼`
- `庇护所.DIY能力槽`
- `庇护所.约束边界`
- `庇护所.编译摘要`

用途：

- 作为 AI 每轮叙事读取的正式状态
- 作为 UI 展示的正式状态

## 8. 扩展翼模块化共识

### 8.1 当前看法

- 旧的“可扩展区域 = 字符串状态”不够用。
- 医疗翼 / 制造工坊 / 载具格纳库未来应视为模块容器，而不是单值字符串。

### 8.2 目标形态

每个扩展翼应至少具有：

- wing_key
- 名称
- tier
- status
- module_slots
- equipped_modules
- custom_name
- custom_desc
- boundary_summary

### 8.3 扩展翼与能力的关系

- 扩展翼是容器层。
- 能力/模块是装配层。
- 等级解锁的是“可建造/可升级/可装配的池子”，不等于直接生效。

## 9. DIY 能力槽共识

### 9.1 保留 DIY，但必须受约束

- DIY 是增强可玩性的关键部分。
- 但 DIY 不能成为无限制开挂入口。

### 9.2 DIY 当前最小要求

- 必须属于某个分类
- 必须有稳定 key
- 必须有明确边界
- 必须有代价或限制
- 必须能被编译为摘要
- 必须可被 prompt 侧引用

### 9.3 DIY 的定位

- DIY 更接近“自定义单槽模块”
- 而不是“自由无限创造新系统”

## 10. 现阶段不做的事

以下内容当前不作为第一优先：

- 兼容现有 `ShelterSection.vue` 的全部约束与展示逻辑
- 立即细化每一个能力/模块的最终文本
- 立即改造全部旧世界书条目
- 立即确定最终 UI 交互样式

当前阶段优先做的是：

- 明确结构
- 明确职责边界
- 明确持久化策略
- 明确世界书回调机制

## 11. 当前开放问题

以下问题尚未定稿，后续必须逐条讨论，否则容易出现冗余和冲突：

### 11.1 蓝图层

- `庇护所升级能力.txt` 是否继续单文件承载，还是拆为多文件注册表？
- 能力包/流派包是否单独建模？
- DIY 蓝图覆盖层允许覆盖哪些字段？

### 11.1.1 世界观配置集（新增）

除庇护所蓝图外，还需要对世界观与文明阶段规则引入少量、可控的静态配置集，以匹配不同主流派的游玩爽点。

当前共识：

- 配置集数量不宜多
- 推荐采用 3 档世界观配置
- 每档世界观配置应同时改写：
  - 外部环境强度
  - 行动力窗口
  - 社会残存度
  - 冲突来源类型
  - 推荐主流派

建议的三档世界观配置：

#### A 档：围猎堡垒型

- 气候：寒冷但未彻底瘫痪外出能力（相较极寒档更高温）
- 特征：自然环境压力下降，但暴徒、袭击者、异变威胁或高频冲突来源增多
- 爽点：战斗、防御、征服、扫荡、清场
- 推荐主流派：`守`
- 次级协同：`扩 / 行`

#### B 档：极寒守成型

- 气候：极端寒冷、高活性雪晶、窗口稀少，外出高度受限
- 特征：资源循环、人口维持、医疗与后勤压力极高
- 爽点：生存、维持、种田、守成、人口保全
- 推荐主流派：`养`
- 次级协同：`管 / 慰`

#### C 档：窗口秩序型

- 气候：一次性暴雪与骤降后，存在若干常规天气窗口期
- 特征：社会生产受损但未彻底归零，人类社会残余结构仍存在
- 爽点：治理、联盟、交易、制度建设、秩序扩散
- 推荐主流派：`管`
- 次级协同：`扩 / 行 / 慰`

注意：

- 世界观配置集不是“能力树”的替代物
- 而是“能力树运行舞台”的静态环境模板
- 同一主分支在不同世界观配置下，玩法体验应有明显差异

### 11.1.2 文明阶段规则的改造方向（新增）

由于开局将允许更强技能和更多流派，因此：

- `文明阶段规则`
- `世界观`

都需要做有限静态改造，以适配新的构筑系统。

当前方向：

- 世界观不再只有单一“永恒暴雪极寒末日”口径
- 而是保留统一灾变母题下的多个静态配置档位
- 文明阶段规则应允许因世界观档位不同而调整：
  - 资源稀缺梯度
  - 行动风险来源
  - 社会残存程度
  - 阶段推进速度
  - 冲突结构（人祸 / 生存 / 治理 / 远征）

### 11.2 点数构筑

- 初始点数由什么决定？
- cost 是否只与等级相关，还是与分类/稀有度共同相关？
- 是否存在分类槽位上限？

### 11.3 线性演化

- 哪些能力允许升级？
- 哪些能力只能开局决定、后续不可改变？
- 扩展翼模块是否允许“拆装替换”？在什么条件下允许？

### 11.4 世界书回调

- 能力 key、扩展翼 key、模块 key 的命名规范如何统一？
- 绿灯条目是逐能力拆分，还是按分类聚合？
- DIY 条目最终采用动态 prompt 注入还是临时世界书条目？

### 11.5 变量写入策略

- 开局 build 何时从 `chat` 变量编译进 `stat_data`？
- 是开局确认后一次性写入，还是允许中间草稿态预览写入？
- 哪些字段只存在于 `chat` 变量，哪些字段必须进入 `stat_data`？

## 12. 当前阶段建议的推进顺序

推荐后续按以下顺序继续讨论和设计：

1. 蓝图 key 体系与命名规范
2. 世界观配置集与文明阶段档位定稿
3. 点数构筑规则与 DIY 槽边界
4. `stat_data.庇护所` 新 schema 定稿
5. `chat` 变量中的开局构筑结构定稿
6. 世界书蓝图拆分/回调策略定稿
7. 编译摘要规则定稿
8. 脚本改造策略定稿

## 13. 当前一句话总结

当前共识可以概括为：

> 开局负责生成并封板“本局庇护所 build”；
> 蓝图层提供静态能力库与回调入口；
> 变量层保存本局正式状态；
> 编译摘要层把结构化状态转成 AI/UI 可消费的摘要与 call key；
> 后续剧情只允许在线性升级规则内演化。
